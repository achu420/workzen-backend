## 2. The actual deletion/restoration contract (Phase A2)

### 2.1 What the frontend's code says the contract should be

`dispatch/row-lifecycle.ts`'s own header comment states the intended design plainly: *"A row whose document has content is not hard-deleted: its row orders are tombstoned (`is_deleted: true`)... so the row disappears from every view but stays restorable from trash. Restoring clears the tombstone; permanent deletion removes the row orders entirely."*

Two genuinely distinct Yjs-level operations exist (confirmed by reading `row-lifecycle.ts` directly, not inferred):
- **`softDeleteRowsInDatabase`**: replaces each view's row-order entry in place with the same `{id, height}` plus `is_deleted: true`. The entry is **not removed** — it is tombstoned and restorable.
- **`removeRowsFromDatabase`**: deletes the row-order entry from the array **outright** (no tombstone left anywhere) and additionally purges the row's local IndexedDB cache/outbox client-side. There is **no restore path** for a row removed this way — once its order-array entry is gone, nothing in the Yjs state says it ever existed in that view.
- Both operations, confirmed by reading `executeOperationWithAllViews`'s call sites, act on **every view's** row_orders uniformly — there is no "remove from view A but keep in view B" primitive at the row_orders level in the current frontend contract. **This is the direct answer to the brief's "removing a row from one view vs. all views" question: that distinction does not exist as a literal membership difference.** Per-view visual differences between two views of the same database come from **Filters** (a view-local, orthogonal query-criteria mechanism, confirmed §1.3 of Task 72's discovery and re-confirmed this task), never from different row_orders membership sets. **Classification: Not supported by the current frontend** (as a row_orders-membership-level feature) — this is not an oversight to fix, it is the real, intentional upstream-matching design (filters already cover the use case).

### 2.2 The decision between the two paths is driven by a backend route that does not exist (new finding, confirmed by direct trace this task)

`useTrashAwareDeleteRowsDispatch` (`dispatch/row.ts:444-556`) is the dispatcher the real "Delete row" UI action actually calls. It decides which of the two operations above to use **per row**, based on `rowDocumentExists(workspaceId, documentId)` (`src/application/row-document/lifecycle.ts:67-77`): if the row's detail-page Document was ever materialized server-side, trash it (soft-delete, restorable); otherwise, remove it outright (not restorable, though the underlying DatabaseRow collab bytes remain intact and orphaned on the server — this part is safe, confirmed §2.3).

`rowDocumentExists()` calls `ViewService.checkCollabExists()` → `GET /api/workspace/{id}/collab/{objectId}/collab-exists` (`view-api.ts:212-219`). **This route does not exist in `server.js`** (confirmed by grep, zero matches). The function's own code explicitly swallows the resulting error and resolves to `false` ("*Errors resolve to false so deletion falls back to the hard-delete path*" — comment at `lifecycle.ts:64-66`).

**Consequence**: against the current backend, `rowDocumentExists()` **always** returns `false` (the HTTP call always fails), so `useTrashAwareDeleteRowsDispatch` **always** takes the non-restorable `removeRowsFromDatabase` branch — even for a row that, if the detail-page feature worked (it doesn't, see §4), would have real document content. The UI's "Delete row" action currently behaves identically to a permanent, non-trash-recoverable unlink for every row, regardless of content, which is a narrower guarantee than the frontend's own documented design intent.

**Is this currently a live data-loss risk?** No — because the companion finding in §4 establishes that a row's detail-page Document can never actually be created or synced against this backend today either (the precondition "row has document content" is currently unreachable). The two gaps are two symptoms of the same missing feature (row-document/orphaned-view backend support), not two independent defects. **Classification: Confirmed defective** (the trash-vs-remove decision logic is wired to a route that doesn't exist, which is a real bug relative to the frontend's documented contract) **but currently non-exploitable in practice** given §4's finding that no row can have real document content yet. A future task that implements §4's missing routes **must** implement this route (`collab-exists`) in the same pass, or it will re-introduce a genuine silent-data-loss-of-discoverability regression (row content preserved on disk, but permanently unreachable through any UI — effectively lost from the user's perspective) the moment row-detail pages start working.

### 2.3 What "safe" currently means, precisely

- **Trashing a row** (when the soft-delete branch is actually taken, e.g. the bulk "Move to trash" action which unconditionally calls `softDeleteRowsInDatabase`, `dispatch/row.ts:369-443`, not gated on `rowDocumentExists()`): fully safe and restorable, confirmed working, zero backend changes needed (generic Yjs mutation).
- **Removing a row** (`removeRowsFromDatabase`, reached today by every single-row "Delete" action because of §2.2): the row vanishes from every view with no UI-reachable restore path, **but its DatabaseRow collab object is never touched on the server** — the underlying data is not destroyed, only unreferenced (re-confirmed, matches Task 62 §2.5's finding exactly, independently re-verified against current `row-lifecycle.ts` source this task).
- **Permanently deleting the DatabaseRow collab object itself**: never happens through any current frontend code path (§1, row 8). **This remains the single most important invariant for any future implementation work: nothing in the real, current frontend contract ever requires the backend to delete a row's actual content. Backend implementation work should never introduce a hard-delete code path for a DatabaseRow object "for completeness" — it would have no caller and would reintroduce exactly the risk this task's brief warns against.**
- **Deleting a parent database or a view containing rows**: confirmed (§1, row 12) to be a pure Folder-tree trash operation; the Database/DatabaseRow collab objects are left completely intact, exactly as with the row-removal case above.

## 3. Relation data model (Phase A3) — exact Yjs structures, traced from source

### 3.1 Relation field configuration — lives on the **Database** collab object (collabType=1)

Per-field `type_option` map, keyed by `FieldType.Relation` (`=10`), confirmed in `src/application/database-yjs/fields/relation/relation.type.ts` and `utils.ts`:

```
YDatabase.fields.get(fieldId).type_option.get('10')   // FieldType.Relation
  .get('database_id')             -> target database id (string)
  .get('is_two_way')               -> boolean
  .get('reciprocal_field_id')      -> field id in the TARGET database's own fields map (omitted if one-way)
  .get('reciprocal_field_name')    -> display name for that reciprocal field (omitted if one-way)
  .get('source_limit')             -> RelationLimit: 0=NoLimit, 1=OneOnly
  .get('target_limit')             -> RelationLimit: 0=NoLimit, 1=OneOnly
```

This is an ordinary `Y.Map` nested inside the Database doc's existing `fields` map — the exact same structure Task 61 already persists/syncs generically for every other field type. **No new backend structure is implied.**

### 3.2 Relation cell values — live on the **DatabaseRow** collab object (collabType=4)

`getRelationRowIdsFromCell()` (`src/application/database-yjs/relation/cell.ts`) reads the cell's `data` key (the same key every cell type uses, per Task 62 §2.3's generic cell shape) and expects a `Y.Array` of row-id strings (with defensive fallbacks for a plain JS array, a JSON string, or a comma-separated string — all legacy/defensive paths, not the primary write shape). The write side (`setRelationCellRowIds`, `dispatch/relation.ts:202-244`) always writes a real `Y.Array<string>`. This is structurally identical to Task 62's §2.3 finding for ordinary cells — **one more per-field `Y.Map` entry inside the row's `cells` map, now containing an array instead of a scalar.** No new backend structure is implied here either.

### 3.3 Reciprocal (two-way) relations — the frontend owns the entire cross-object write, confirmed by direct trace

`dispatch/relation.ts` (1,180 lines) implements the full two-way-relation lifecycle entirely client-side:
- **Creating a two-way relation field** (`useUpdateRelationTypeOption`, `~line 852-1050`) opens the **target** database's own Yjs doc (`loadRelatedDatabaseDoc()`, `~line 393-442`) and writes a brand-new reciprocal field directly into that OTHER Database object's `fields` map (`createRelationField`/`addFieldToAllViews`), then writes the reciprocal field id back into the source field's own `type_option`. Two separate Database collab objects are mutated, each as an ordinary Yjs transaction, each independently synced over its own existing collabType=1 WS channel.
- **Editing a relation cell with `is_two_way` set** (`useUpdateRelationCellDispatch`, `~line 674-845`) opens the **target row's** own DatabaseRow doc (via `loadRowDoc()`, which uses the caller's `rowMap` cache or creates/hydrates a fresh row doc) and writes the mirrored cell value into that row's reciprocal field, honoring `RelationLimit.OneOnly` eviction rules (`applyRelationCellChanges`) on both sides.
- **Resolving which database/view to open for an arbitrary `database_id`** (`loadRelatedDatabaseDoc`'s `getViewIdFromDatabaseId` callback) is implemented in `useDatabaseIdentity.ts:184-238`, and its primary path is the **WorkspaceDatabase catalog** (`getViewIdFromWorkspaceCatalog`) — the exact catalog Task 64 already fixed server-side, with zero relation-specific code. A legacy fallback path (`resolveLegacyRelationViewId`) exists for template-duplicated workspaces, out of scope here.
- **Creating a brand-new row directly from a relation picker, in a different database** (`createRowInRelatedDatabase`, `dispatch/relation.ts:1068-1180`) calls `createCloudRow()` — **the exact same atomic REST endpoint Task 62 built** (`POST /v2/database/{databaseId}/row/default`), just targeting the related `databaseId` instead of the one currently open. **No new route is implied by this capability at all** — it is a straight reuse.

**This confirms the headline finding of Phase A4 directly**: every relation write the frontend performs — field creation, reciprocal field creation, cell writes, reciprocal cell mirroring, limit enforcement, even inline row creation from a relation picker — is expressed as either (a) an ordinary Yjs mutation on a Database or DatabaseRow object already covered by the existing generic collabType=1/4 WS admission path, or (b) a call to the row-creation REST endpoint Task 62 already implemented. The one piece of genuine cross-object orchestration (which database/row to open, and binding its WS sync) is entirely client-side logic reusing the existing catalog (Task 64) and the existing per-object WS binding machinery (Task 71's fix is directly load-bearing here, see §5).

### 3.4 Relation behavior when the referenced row is unavailable

Confirmed by trace: `getLiveDatabaseRowIds()`/`getLiveRelationRowIds()` (`src/application/database-yjs/relation/row-orders.ts`) compute "live" row membership as the union of every view's row_orders entries with `is_deleted` false. A relation cell's stored row ids are **never pruned** when the referenced row is soft-deleted, removed, or otherwise made unavailable — the dangling id simply fails to resolve to a live row and the UI renders a graceful fallback (`RelationRowItem.tsx`: an "Untitled"-style placeholder for a row that resolves but has no title; a loading skeleton while in flight — no crash path found for a row that never resolves at all, confirmed by reading the full component). **Classification: Confirmed working** (graceful degradation, consistent with "never destroy data because a reference became unreachable" — dangling relation ids are inert, not auto-cleaned, which is itself the correct, safe behavior per this task's own stated priority).

## 4. Row-detail-page backend gap (Phase A1 #11 / Phase A2, sharpened this task)

This generalizes and sharpens Task 62's §2.6/§8 deferral (which only said "not created or managed, not exercised") into three concretely missing backend pieces, each confirmed absent by direct grep of `server.js` this task:

1. `POST /api/workspace/{workspaceId}/orphaned-view` — materializes the row-document's Folder-tree page entry (`{"row_document":{"source":{database_id, database_view_id, row_id}}}` in `extra`) and returns the Document's initial `doc_state`. Called only from `ensureRowDocumentView()`, which itself is currently only invoked from the row-peek's **Favorite button** handler (`RowPeekDocumentActions.tsx:76-93` — the only production call site found this task; `GalleryPreview.tsx`/`DatabaseTemplateButton.tsx`/`RightMenu.tsx` were also checked and do not call it unconditionally on open).
2. `GET /api/workspace/{workspaceId}/collab/{objectId}/collab-exists` — the existence probe `rowDocumentExists()` needs (§2.2).
3. **Document WS admission's implicit precondition**: `server.js:1859-1871` (collabType=0 branch) requires `store.getPage(pageId)` to resolve to a real Folder-tree row belonging to the caller's workspace before admitting **any** sync frame for that object id — confirmed by direct read of the current handler. A row-document's deterministic id (`uuidv5('document_id', rowId)`) has no Folder-tree page entry unless route (1) above has run. **Without route (1), a row's detail-page body content cannot be synced or persisted at all** — not merely "deferred," but actively rejected (1008 close) the moment a client tries.

**Net effect, confirmed by chaining the three points above**: opening a row and typing into its detail-page body today will fail silently from the backend's perspective (the WS frame is rejected) the first time the client actually tries to sync that content — no row, under the current backend, can ever have real persisted detail-page content. This closes the loop with §2.2's finding (the trash-decision route also depends on this same missing feature) and is the single largest confirmed gap found this task. **Classification: Missing.**

This is **not** a relation-specific finding, but it is directly relevant to row lifecycle completeness (explicitly requested in Phase A1, operation "edit row detail-page content") and belongs in any implementation scope decision alongside relations.

## 5. Relation/rollup architectural boundary (Phase A4)

Re-confirmed, this task, by direct code trace (not solely inherited from Task 60's architecture document, though fully consistent with it):

- **Rollup and Formula computation are entirely frontend-owned**, confirmed by reading `src/application/database-yjs/rollup/computed.ts` and `formula/*`: values are computed live, in-browser, by walking the relation graph (`readRelationMembership`, `getRelationRowIdsFromCell`) and reading each related row's own cell data directly out of its Yjs doc — with real circular-dependency detection (`ComputedDependencyError`) and a hop-depth limit (64), entirely client-side. **No rollup or formula result is ever written back into any persisted Yjs structure** as an ongoing, synced value (the one exception found, `formula/materialize.ts`, is a one-shot CSV-export snapshot conversion, unrelated to row lifecycle or ongoing sync — not a counter-example to this finding). **The backend does not need to know these field types exist at all** and should not be given any computation responsibility for them, consistent with Task 60's architecture document's explicit warning against building a formula/rollup/query engine.
- **Backend source has zero relation/rollup-aware code**: grepped `server.js`/`storage.js`/`postgres-storage.js`/`postgres-collab-repository.js`/`database-document.js`/`database-row-document.js` this task — the only matches are pre-existing **comments** documenting these field types as explicitly out of scope for Database/DatabaseRow doc initialization (they don't need special initialization; a field of any `FieldType` value, including 10/15/16/17/18/19, is just another entry in the generic `fields`/`type_option` maps, written by the frontend's own Yjs mutation and persisted/synced with zero awareness of its semantic type — exactly Task 61's "generic Yjs admission" finding, now independently re-confirmed for Relation specifically).
- **Postgres parity is already complete for relation data with zero additional code**: confirmed by reading `postgres-collab-repository.js` — both Database and DatabaseRow state are persisted as one opaque `Y.encodeStateAsUpdate(doc)` binary blob per object, exactly mirroring JSON mode's "store the whole encoded doc" convention. A relation field's `type_option` and a relation cell's row-id array are just more bytes inside that blob — Postgres mode already carries them correctly, with no schema or code change required (same conclusion Task 72 reached for view-config content).
- **The one piece of relation functionality that depends on an already-fixed backend capability**: cross-database relation resolution (`getViewIdFromDatabaseId`) depends on the WorkspaceDatabase catalog, which Task 64 already fixed. No further catalog work is implied.
- **The one piece of relation functionality that reuses an already-implemented backend capability**: inline row creation from a relation picker (§3.3) reuses Task 62's row-creation REST endpoint verbatim, targeting a different `databaseId`. No further row-creation work is implied, **provided the target database belongs to the same, caller-authorized workspace** — re-confirmed: `createCloudRow()`'s target databaseId is still subject to the existing `store.getDatabaseCollab(workspace.id, databaseId)` workspace-scoping check (Task 62 §2.8), so a relation pointing at a database in a different workspace (if that were ever reachable through the UI, which it is not — `getViewIdFromWorkspaceCatalog` is itself workspace-scoped) would correctly fail authorization, not silently cross a workspace boundary.

**Conclusion, stated plainly per the brief's explicit instruction**: relation fields (configuration, cell values, two-way reciprocal mirroring, limit enforcement, cross-database row creation) are **already fully supported by the existing generic Yjs/WebSocket/Postgres-blob admission pipeline with zero relation-aware backend code required**, in exactly the same pattern Task 72 found for database view configuration. **Rollup/Formula are entirely frontend-computed and require no backend storage or computation support at all.** No new query engine, no new collab-object type, no new protocol message, and no new Postgres schema are needed for anything investigated in this phase.

## 6. Collaboration/concurrency review (Phase A5)

- **DatabaseRow content updates** (cell edits, including relation cells): ordinary collabType=4 WS admission, unchanged, already covered by Tasks 61/65/66/68's fan-out/recovery work. **Confirmed working**, not re-tested with a dedicated new scenario this task (no code changed that would affect it; relying on the existing `test:database-row-collab` 11/11 pass re-confirmed §0).
- **Database-level row-order changes** (move/trash/restore/remove): ordinary collabType=1 WS admission, same conclusion.
- **Relation changes affecting TWO different row documents** (the brief's explicit cross-object question): confirmed by §3.3's trace to be two **independent** Yjs transactions against two **independent** collab objects (the source row and the target row, potentially in two different databases) — each persisted/fenced by its own object's `mutate()` lock, with **no cross-object atomic transaction**. This is architecturally identical to the pre-existing trait Task 72 §4 already documented for HTTP atomic-creation routes not fanning out live to already-open peers, generalized one step further: a two-way relation write is not all-or-nothing across both objects. A crash between committing the source cell and the reciprocal cell could, in principle, leave a temporarily one-sided link. **This was not newly introduced by relations** — it is the same single-writer-per-object, no-cross-object-transaction model every other multi-object interaction in this codebase already has (e.g., row creation's own row+row_orders atomicity is scoped to ONE Database object, per Task 62 §2.4, never across two). **Classification: Confirmed working, with the same pre-existing architectural limitation as everywhere else in this codebase** — not a relation-specific regression, and per the brief's own instruction not to invent new fan-out/atomicity mechanisms where the existing pipeline already handles the general case adequately for a self-hosted, typically-small-team deployment.
- **Updates to two separate databases** (e.g. editing a database's own fields while a relation write targets it from another database): both are ordinary, independent collabType=1 WS sessions; no shared state beyond what's already serialized per-object. **Confirmed working.**
- **Object binding and sibling-object traffic, including Task 71's fix**: relation editing is the clearest real-world trigger for exactly the scenario Task 71 fixed — a single browser tab simultaneously maintaining live WS bindings for the **source** Database doc, the **source** row doc, the **target** Database doc, and the **target** row doc (up to four distinct collab objects bound to sync in the same tab during one relation edit, confirmed by `loadRelatedDatabaseDoc`'s `bindViewSync` call and `loadRowDoc`'s row-doc creation in §3.3). Task 71's "re-assert binding immediately before send" fix in `useSyncContextLifecycle.ts`/`useSync.ts`/`AppSyncLayer.tsx` is directly load-bearing for this feature to work correctly at all — **re-confirmed present and untouched this task** (file contents not re-diffed line-by-line this task beyond the `git status` check in §0, which confirms no regression). **Classification: Confirmed working** (the fix already exists and was built generically, not relation-specific, but relations are the clearest consumer of its correctness).
- **Sender ack/peer fan-out, reconnect/persistence recovery**: unchanged, generic, already covered by Tasks 66/68. No relation-specific gap found.

## 7. Security/authorization implications

No new authorization surface is implied by anything found in this phase. Relation cross-database access is gated exactly where ordinary database access already is: `requireWorkspace()` (session/workspace membership) plus `store.getDatabaseCollab(workspace.id, databaseId)` (workspace-scoped existence check, Task 62 §2.8) for any row-creation call, and the WorkspaceDatabase catalog's own workspace-scoping (Task 64) for view/database discovery. A relation field pointing at a database id outside the caller's own workspace cannot be created through the real UI (the picker only ever offers databases the catalog resolves within the current workspace) and would be rejected by the existing checks even if attempted directly. **No change recommended.**

## 9. Recommended implementation scope (for a future task, pending approval)

**In scope, if approved:**

Any implementation task should explicitly verify this with new tests (two-way relation creation, cross-database cell write, relation cell surviving restart, Postgres parity for a relation field) rather than writing new server logic, mirroring Task 72's own "write tests proving the existing pipeline already works" pattern.

Row duplication (§1 row 9) — a real, reachable gap, but (per Task 62's own precedent for excluding it, and consistent with this task's "flag disproportionate scope" instruction) it is a materially larger, separate contract (template graphs, embedded documents) and is recommended as its **own** future task, not folded into this one.
