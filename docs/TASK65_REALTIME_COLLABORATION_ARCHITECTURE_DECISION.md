## 1. Upstream architecture, summarized (full detail in the Stage-1 audit)

Upstream AppFlowy-Cloud ships two realtime stacks; the one AppFlowy-Web's real client actually talks to over `/ws/v2/{workspaceId}` is a **workspace-scoped actor** (`Workspace`, one per workspace, `ws2/actors/workspace.rs`) that:
1. Admits a client's `Update` by checking per-session write permission, then writing it to a Redis Stream keyed by workspace (`CollabManager::publish_update`, `collab/collab_manager.rs:239-278`) — no ack is sent to the sender in this live protocol.
2. Separately, as the stream's own subscriber, reads that write back and **iterates every other currently-joined session for that workspace** (`sessions_by_client_id`, minus the origin), re-checks read permission per target session/object, and pushes the same `Update` frame directly to each (`workspace.rs:394-461`).
3. Durability to the long-term (Postgres-backed) store is asynchronous — a periodic snapshot, decoupled from both admission and broadcast.
4. Awareness/presence follows the identical "iterate other joined sessions, skip origin, push" shape through a second, parallel Redis stream.

The legacy `/ws/v1` stack (`group/`, `rt_server.rs`) does the same thing per-collab-object instead of per-workspace, and does send an ack (gated on the Redis write, not on long-term persistence) — included in the audit because it is real, shipped code and the direct ancestor of the v2 design, but it is not what the paired frontend uses.

**The CRDT/protocol/data-model layers (Yjs/Yrs, the protobuf wire schema, the Document/Database/WorkspaceDatabase/DatabaseRow collab-object graph) are unchanged from Task 60/60.5's findings and are not revisited here** except where this task's deeper trace adds detail (e.g. `Rid` = literal Redis Stream message id, now confirmed at the exact call site rather than inferred from a frontend code comment).

## 2. This backend's architecture, summarized (full detail in the Stage-2/3 gap analysis)

A single Node.js process holds a flat, unscoped `websocketPeers` set across every workspace and object (`server.js:1575`). Content updates (`Document`/`Database`/`DatabaseRow`) are admitted through a persist-before-ack pipeline (durable write to JSON-file or Postgres storage, synchronously, before any response — stronger than upstream's v2 path, which has no ack and only guarantees "written to Redis") and acked directly to the sender only. Awareness updates are relayed to other peers matching the same `workspaceId`+`objectId` via a filtered scan of `websocketPeers` — this is the one piece of "live push to other connected sessions" already implemented, and it is structurally the same idea as upstream's broadcast step, just scoped by direct peer-set filtering instead of a maintained per-object/per-workspace roster, which is adequate at this backend's deliberate single-process scale.

## 3. Sync-flow comparison and exact missing capability

Full table in the Stage-2/3 document. **The single genuine, user-visible gap found**: content `Update`s are never pushed to other already-connected peers for any collab type — only awareness is. Everything else compared (initial sync, state-vector exchange, admission validation, ack/persistence timing, duplicate handling, Rid semantics, offline edits, workspace isolation) is either equivalent-by-design, a pre-existing documented simplification, or an area where this backend's own guarantees are stronger than upstream's live v2 protocol, not weaker.

## 4. Root cause (restated from the Stage-2/3 document, with its evidentiary basis)

Verified, not assumed: the frontend (`AppFlowy-Web/src/application/services/js-services/sync-protocol.ts:220-254,384-400`) already applies any incoming `Update` frame for an open object uniformly, regardless of origin — it needs **no change**. The wire message shape needed is identical to the ack frame this backend already sends to the sender and identical to upstream's own broadcast frame — **no protocol change** is needed. The cause is narrowly: the three `Update`-admission code paths in `server.js` (Document ~1780-1819, Database ~1895-1973, DatabaseRow ~2056-2134) never consult the `websocketPeers` registry, even though that exact registry is already correctly iterated for the sibling `awarenessUpdate` path in the same three (plus a fourth generic) locations. This is a scoped, mechanical omission in an otherwise-proven pattern, not evidence of a missing architectural concept, a missing piece of infrastructure, or a deeper design gap.

## 5. Architectural options evaluated

### Option A — Adopt upstream's collaboration server/components directly (without the whole AppFlowy Cloud backend)

Re-verified this task (not merely re-cited from Task 60.5): `services/appflowy-collaborate` (both the v1 `group`/`rt_server` stack and the live v2 `ws2`/`collab_manager` stack) is an Actix-web-coupled Rust module, not a crate packaged for standalone embedding. `CollabManager::new` (`collab/collab_manager.rs`) is constructed with a `ThreadPoolNoAbortBuilder` thread pool, a `CollabAccessControl` trait object wired to AppFlowy-Cloud's own `access-control` crate, a `CollabCache` backed by AppFlowy-Cloud's own Postgres/S3 schema, a Redis `ConnectionManager`/`StreamRouter`/`AwarenessGossip`, and an `IndexerScheduler` tied to AppFlowy-Cloud's own embeddings pipeline — i.e. even the *live* v2 stack (not just the legacy v1 one Task 60.5 examined) is just as hard-coupled to AppFlowy-Cloud's surrounding schema/auth/Redis as previously found. No FFI/napi/WASM Node bindings were found this task either (not re-searched exhaustively this task, but nothing in the newly-read `ws2`/`collab_manager` source introduces any such binding; the conclusion stands). **Running this as a standalone process alongside the Node backend would still require Redis** (both stacks hard-require it — it is not an optional cache, it is the sole mechanism by which an accepted update becomes visible to anyone, including the sender's own broadcast loop) **and would still require adopting or adapting AppFlowy-Cloud's `af_workspace`/`af_user`/permission schema** for the access-control checks `Workspace`'s session roster performs at every single broadcast send. Verdict: **not newly viable since Task 60.5; if anything, confirmed harder than previously documented**, because the live v2 stack this task traced is at least as entangled as the v1 stack the prior audit focused on, and it additionally has a mandatory Redis dependency with no optional/degraded mode found in source.

### Option B — Adapt the existing Node.js architecture to implement upstream's actual observed behavior

This is **not** "add a generic WS broadcast loop because it seems obviously needed" — it is, specifically, **replicate the exact pattern this backend's own codebase already implements correctly for `awarenessUpdate`, applied to the `Update` message path for all three collab types**: after a content update is durably admitted (unchanged — persist-before-ack stays exactly as proven by Tasks 42-46/61/62), iterate `websocketPeers` filtered to the same `workspaceId`+`objectId`, excluding the sender, and send each matching peer the same `Update` frame shape already sent to the sender as its ack. This mirrors upstream's actual mechanism (§1) at the correct level of fidelity for this backend's deliberate single-process scope: upstream's "live roster of other joined sessions, minus origin, permission-checked, pushed to" becomes, in a single process with no cross-instance concern, "live set of other open sockets matching this object, minus origin, pushed to" — the same idea, intentionally simplified by dropping only the cross-process coordination upstream needs Redis for and this backend does not currently claim to need. No new infrastructure, no new protocol, no frontend change — confirmed by §3/§4 above. This also naturally extends to reusing the existing `requireWorkspace()`-based authorization check (already the sole real authorization primitive, Task 60) at send time if desired, matching upstream's per-send permission re-check, without inventing a new authorization model.

### Option C — Reuse selected upstream components/concepts without the full Rust service

Already happening and should continue unchanged: the Yjs/Yrs CRDT family, the protobuf wire message shapes, and the conceptual collab-object typing (document/database/workspace-database/folder/database_row/awareness) are already mined from upstream (Task 60.5 §4/§11). This task adds one new concept worth deliberately borrowing (not code, a *pattern*): upstream's "broadcast is a live roster iterated at update-visibility time, decoupled from durability" shape, which Option B already proposes adopting in substance. There is no new, previously-unconsidered component surfaced by this task's deeper trace that would be reusable as a discrete adoptable unit beyond what B already captures — the `UpdateStreamMessage`/Redis-stream machinery is not separable from Redis itself, and the `Workspace` actor's permission-caching (`WorkspaceSessionHandle`, `workspace.rs:776-920`) is a reasonable idea but not a gap this backend currently has (it already gates every write through `requireWorkspace()`, just not currently at broadcast-send time for awareness, which is an existing, pre-dated, documented simplification, not newly found here).

### Option D — Preserve the current pull-based model, on the grounds that it may be acceptable for this product's requirements

Considered and **rejected as the final answer, but only after being taken seriously**: the current model is not *incorrect* (eventual consistency is always reached on next `SyncRequest`, and this was true before this task and remains true), and Task 60.5 already established that this backend deliberately favors simplicity over upstream's scale-out machinery. However, D does not hold up once the frontend evidence (§3 above) is accounted for: AppFlowy-Web's UI is built, end to end, on the assumption that a server can push unsolicited updates to an open document (`handleUpdate` applies any `Update` frame unconditionally; there is no "pull to refresh" UI concept anywhere examined). A real two-user (or two-tab) collaborative session with this backend today silently fails to look collaborative — Client B's screen will not update while both are looking at the same Document/Database/Row, which is the single most basic expectation of a product whose entire value proposition is "real-time collaboration," and which Task 63/64 already flagged as a real, reproduced symptom (not speculative). Preserving D would mean shipping a backend that satisfies every test in this project's suite yet visibly fails the product's core promise in the most basic two-user scenario. D is rejected because the evidence does not support "acceptable," not because complexity-aversion was wrong as a general instinct — in fact Option B is chosen precisely because it is the *lowest-complexity* fix, not the most feature-complete one.

### Option E — Any other evidence-supported approach

Considered and rejected: a **BroadcastChannel-only fix** (relying on the frontend's existing same-origin-tab `BroadcastChannel` relay, already used for sibling-tab sync per the Stage-1 audit §3's reference to `bcCollabMessage`) was considered, since it requires zero backend change at all — but it only solves the same-browser-multiple-tabs case, not the actual two-different-users/two-different-browser-contexts case Task 63/64 explicitly tested and that is this product's primary collaboration scenario; rejected as insufficient, not as wrong in kind. A **polling-based refresh** (client periodically re-sends `SyncRequest` on a timer while a doc is open) was considered as a lower-engineering-cost alternative to B — rejected because it would require a *frontend* change (none of the examined frontend code polls on an interval; it is purely event-driven), would contradict the task's instruction not to introduce frontend changes without being asked, and would still be strictly worse than B on latency and server load for equivalent correctness. Adopting a **third-party pub/sub library** (e.g. a lightweight in-process EventEmitter abstraction, or introducing Redis solely for this) was considered and rejected as unnecessary complexity for a single-process deployment target — `websocketPeers` already is a complete, correct, zero-dependency substitute for the single-process case, and introducing Redis now would be adopting upstream's scale-out infrastructure to solve a problem that does not require scale-out to solve.

## 6. Recommendation

**Option B.** Rationale, scored against the brief's evaluation dimensions:
- **Correctness**: preserves every existing durability/dedup/validation guarantee untouched (Tasks 42-64's test suites are the regression gate); only adds a new, additive send step after admission already succeeds.
- **Upstream compatibility**: replicates upstream's actual observed behavior (§1/§4) at the correct fidelity for this backend's scope, rather than inventing a different mechanism or ignoring the behavior entirely.
- **Protocol compatibility**: zero wire-protocol change — reuses the existing `Update` message shape, proven compatible with the real AppFlowy-Web client (§3 of the gap analysis, and Task 60.5's field-for-field confirmation).
- **JSON and Postgres compatibility**: the fix is purely in the WebSocket fan-out layer (`server.js`), orthogonal to which storage backend accepted the update — applies identically regardless of `STORAGE=json` or `STORAGE=postgres`.
- **Concurrency handling**: unaffected — admission order is still serialized by the existing single-writer `mutate()` queue; broadcast is a pure side effect of an already-decided, already-ordered admission.
- **Recovery**: unaffected — a peer that misses a broadcast (e.g. a message dropped mid-send, or was briefly disconnected) still self-heals on its next `SyncRequest`, exactly as today; broadcast is explicitly an additive latency improvement, not a new correctness dependency.
- **Security/workspace isolation**: can and should reuse the exact same `workspaceId` scoping the awareness relay already performs, with the option (recommended, not mandatory for a minimal fix) to also reuse `requireWorkspace()`-equivalent authorization at send time, matching upstream's per-send permission re-check without inventing a stricter model unilaterally.
- **Deployment/new infrastructure**: none — no new process, no new dependency, no Redis, no schema change.
- **Scalability**: honestly bounded — this remains a single-process solution, exactly like today; it does not and is not claimed to solve multi-process fan-out (an explicitly separate, deferred concern per Task 60.5's Strategy A, unchanged by this task).
- **Complexity**: the smallest change that closes the actual, evidenced gap — extending an existing, already-tested pattern to three more call sites, not introducing a new subsystem.
- **Maintainability**: one more instance of a pattern already present and understood in the same file, rather than a second, differently-shaped mechanism.
- **Licensing**: no upstream code or schema is adopted; nothing changes about this backend's current clean-licensing posture (Task 60.5 §13's open questions — the backend's own unstated LICENSE, and `collab-protocol.js`'s AGPL-provenance question — are unaffected by this task and remain open exactly as previously flagged, not newly implicated by Option B since no new protocol surface is introduced).

## 7. Required changes if approved (scope only — not performed under this task)

1. In each of the three `Update`-admission success paths in `server.js` (Document, Database, DatabaseRow — the exact blocks cited in §4), after the existing ack-to-sender frames are sent, add a send step that iterates `websocketPeers`, filters to `peer !== websocket && peer.readyState === 1 && peer.workspaceId === websocket.workspaceId && peer.objectId === <thisObjectId>`, and sends each matching peer the same `Update` frame (or an equivalent one built from the already-computed `accepted.*` fields) — i.e. the same filter predicate already used for `awarenessUpdate`, applied at the same call sites.
2. Decide (explicit open decision, not resolved by this document) whether the broadcast frame to peers should carry the full post-admission Yjs update (simplest, matches what's already computed for the sender's own ack) or a server-recomputed diff against each peer's last-known state vector (upstream does not attempt the latter in the broadcast path either — it broadcasts the same bytes to everyone, relying on Yjs's own idempotent/CRDT-safe application — so the simplest option is also the upstream-faithful one).
3. No changes to `storage.js`, `postgres-storage.js`, `postgres-collab-repository.js`, `auth.js`, or any persistence/ack/validation code — the fix is additive and confined to the post-admission send step.
4. No frontend changes (per §3/§4's evidence) and no protocol/schema changes (`collab-protocol.js` unchanged).
5. New tests required (not yet written — this task did not write any code): a two-WebSocket live-broadcast fixture per collab type (mirroring the existing `postgres-database-multiclient.test.js` shape, but asserting the peer *does* receive the frame instead of asserting it currently does not), for both JSON and Postgres storage modes, plus a real two-browser-context verification analogous to Task 64's methodology.

## 8. Infrastructure implications

None beyond what exists today. No Redis, no second process, no new deployment artifact, no schema migration. This is the central practical advantage of Option B over Option A/C's upstream-adoption variants.

## 9. Licensing implications

None newly introduced. Task 60.5's two open licensing questions (this backend's own unstated LICENSE; whether `collab-protocol.js`'s reconstruction of an AGPL-licensed `.proto` schema's field shapes carries AGPL obligations) remain exactly as previously flagged — Option B does not touch `collab-protocol.js`'s schema and does not adopt any additional upstream source, so it neither resolves nor worsens either open question. Resolving those two items remains independently recommended (as Task 60.5 already said) but is out of this task's scope.

## 10. Risks and migration strategy

- **Risk**: a naive implementation could re-send a peer's own update back to itself if the peer-filter predicate is wrong — mitigated by reusing the exact, already-correct filter predicate from the awareness path verbatim (`peer !== websocket`), not re-deriving it.
- **Risk**: broadcasting before confirming the peer can still validly receive it (e.g. a peer that has since lost access) — upstream re-checks read permission at every broadcast send (`workspace.rs:437`); this backend's current awareness relay does not re-check beyond `workspaceId` equality (a pre-existing, documented simplification, Task 60). Recommendation for whoever implements this: at minimum preserve parity with the existing awareness relay's checks; adding a stricter per-send permission check is a reasonable enhancement but should be an explicit, separately-reviewed decision, not silently bundled into this fix.
- **Risk of regression**: none expected to existing single-peer behavior, since the change is purely additive (new peers receive a frame they did not receive before; the sender's existing ack/manifest flow is untouched). The full existing regression suite (§11 below) is the safety net and must stay green.
- **Migration**: none needed — this is not a data migration or schema change; it is a behavioral addition that can be deployed and rolled back independently of persisted state.
- No feature flag is strictly required (the change is safe-by-construction for a single-process deployment), but one could be added if the implementer wants a kill switch; not mandated by this decision.

## 11. Testing strategy

Required before considering Option B done (for a future implementation task, not this one): re-run the full existing baseline (§12 below) unmodified-and-green as the regression gate; add the new two-peer live-broadcast fixtures described in §7 item 5 for all three collab types in both storage modes; extend `test/collab-conformance.js` only if a new conformance claim is being made (likely not needed, since no protocol change occurs); perform a real two-browser-context manual/Playwright verification analogous to Task 64's methodology, specifically for the "already-connected second client sees Client A's edit without reconnecting" scenario, since that is the exact symptom this task was asked to diagnose and that observation (not just a unit test) is what will give final confidence the product-level promise is met.

## 12. Explicitly rejected approaches and why (consolidated from §5)

- **Option A** (adopt upstream's collaboration server/components wholesale or as a sidecar service) — rejected: both upstream realtime stacks (confirmed again this task, including the live v2 one, not just the previously-examined legacy v1 one) are hard-coupled to Redis and to AppFlowy-Cloud's own auth/workspace/permission schema; no embeddable packaging exists; adopting it would reintroduce exactly the dependency burden this project exists to avoid, for a gap that does not require it.
- **Option C as a standalone recommendation** — not rejected outright, but folded into B: there is no additional discrete upstream component this task found worth adopting beyond the pattern B already captures.
- **Option D** (do nothing / accept pull-based sync as sufficient) — rejected: the frontend evidence shows the product's basic two-user collaborative scenario visibly fails to feel collaborative under D, and this was independently reproduced (not merely inferred) via Task 63/64's and this task's own live multi-peer test run.
- **BroadcastChannel-only fix** — rejected: solves only the same-browser multi-tab case, not the cross-user/cross-browser-context case that is this product's primary scenario.
- **Client-side polling** — rejected: requires an unrequested frontend change, contradicts the event-driven design already present, and is strictly worse than B on both latency and load for the same correctness outcome.
- **Introducing Redis/a message broker now** — rejected: solves a multi-process-coordination problem this backend does not currently have or claim to need, at the cost of new infrastructure, for a gap whose root cause (§4) is a missing single-process fan-out step, not a missing broker.
