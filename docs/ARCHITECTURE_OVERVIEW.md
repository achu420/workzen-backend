# Architecture overview (Task 58)

This supersedes the scope of the root-level `ARCHITECTURE.md` (which only covers the JSON/Postgres CRUD split as of early tasks) by adding the collaboration, version-history, and CORS layers built in Tasks 33-57, and by recording explicit risk/decision labels per the Task 58 mandate. It does not replace `ARCHITECTURE.md`; both may coexist, but this is the current reference.

## 1. Components

- **`server.js`** — single Node.js ESM HTTP(S)+WebSocket process. Owns routing, CORS, auth-token checks, request validation, and the WebSocket upgrade/handshake for both `/ws/v2/{workspaceId}` and `/ws/{workspaceId}` (aliased to identical handling since Task 52).
- **`auth.js`** — password hashing (`scrypt`, 16-byte random salt, `timingSafeEqual` verification) and opaque session/refresh token issuance (`randomBytes(32)` base64url, SHA-256 stored hash).
- **`storage.js`** — JSON-mode repository: in-memory state + atomic temp-file-write-then-rename persistence. Single-writer serialization via `mutate()`, which is also the exact point where Rid allocation and persist-before-ack both happen.
- **`postgres-storage.js`** / **`postgres-collab-repository.js`** — Postgres-mode repository with the same generic method names as `storage.js` (so `server.js` needs zero mode-specific branching), using `pg.Pool`, explicit `BEGIN`/`COMMIT`/`ROLLBACK` transactions, and `finally`-guaranteed client release.
- **`postgres-migration-lock.js`** (added Task 59) — deterministic advisory-lock key derivation (`deriveMigrationLockKey`, SHA-256 of `current_database()`, folded into a signed bigint) plus `acquireAdvisoryLock`/`releaseAdvisoryLock` helpers (bounded `pg_try_advisory_lock` retry loop, explicit `pg_advisory_unlock`). `openPostgresStore()` acquires this session-level lock on its dedicated migration client before touching any schema, rechecks a new minimal `schema_migrations` tracking table under the lock, runs only still-pending migration files (each in its own transaction, so a failed file is never recorded as applied), then releases the lock and returns the client to the pool before handing back the repository. This replaced a pre-Task-59 defect where every `openPostgresStore()` call blindly reapplied the full migration DDL text with no coordination between processes at all — reproduced with two real OS processes against a fresh database (one hung indefinitely; see `docs/APPFLOWY_TASK59_REPORT.md` for the full reproduction and fix verification, including a genuine two-process + crash-mid-lock recovery run).
- **`database-document.js`** (added Task 61) — Database collab-doc initializer (`createInitialDatabaseCollab`), mirrors `page-document.js`'s role for Documents exactly: builds the initial Yjs state for a brand-new Database object (`doc.getMap('data').get('database')` with `fields`/`views`/`metas`, one seeded primary `RichText` field, one inline Grid view with empty but correctly-typed `row_orders`/`filters`/`sorts`/`groups`/`calculations`), returns `{documentState, stateVector, collabVersion}`.
- **`database-row-document.js`** (added Task 62) — DatabaseRow collab-doc initializer (`createInitialDatabaseRowCollab`), same role one level down: builds the initial Yjs state for a brand-new DatabaseRow object (`doc.getMap('data').get('data')` — the row, aliasing the same raw key as the root map's own name — with `id`/`database_id`/`visibility`/`height`/timestamps/optional attribution, a `cells` `Y.Map` seeded from the creation request's frozen cell data, and an always-present but empty `meta` `Y.Map`), returns `{documentState, stateVector}` (no `collabVersion` — rows carry no independent version-tracking concept, see §6 below).
- **`collab-protocol.js`** — source-derived subset of AppFlowy's protobuf collab messages (envelope encode/decode, SyncRequest/Update/manifest framing). Unchanged this task — confirmed collabType-agnostic already (the protobuf schema carries `collabType` as a plain `int32`, with no type-specific message shapes), so the new Database admission path (Task 61) required zero changes here.
- **`collab-repository.js`** — the original in-memory offline-collab prototype (Task 17); retained for its own test suite, not the production durability path.
- **`migrations/*.sql`** — numbered, explicitly-listed (not globbed) SQL files; `001_initial.sql` through `007_database_and_database_row_collab.sql` at last count (Task 63). **Important operational note (re-confirmed this task):** adding a new migration file requires also adding its filename to the `MIGRATION_FILES` array in `postgres-storage.js`, or it silently never runs (Task 53 lost time on this). All existing migration statements are plain, idempotent, transaction-safe DDL (`CREATE ... IF NOT EXISTS`, `DO` blocks with exception handlers, `DROP CONSTRAINT IF EXISTS`) — none use `CREATE INDEX CONCURRENTLY` or other statements incompatible with running inside a transaction, which is what makes Task 59's per-file-transaction + session-level-advisory-lock design safe.

## 2. Data flows

### Document edit (WebSocket)
Client → WS frame → `server.js` auth/membership check → `store.acceptPageCollabUpdate()` → Yjs merge + Rid allocation, inside `mutate()` (JSON) or a single Postgres transaction → durable write completes → **only then** is the ack frame built and sent. This ordering (persist-before-ack) is proven by real fault injection (Task 44: delayed-persist and failed-persist tests), not just static code reading.

### Document edit (HTTP full-sync/batch)
Same `acceptPageCollabUpdate()` function, called from a different route. Task 43 proved both lanes converge on one durable state when used on the same document in sequence.

### Database edit (WebSocket) — added Task 61
Client → WS frame (`collabType: 1`) → `server.js`'s new, additive Database branch (inserted between the existing Document branch and the existing WorkspaceDatabase gate, touching neither) → `store.acceptDatabaseCollabUpdate()` → same `preparePageCollabUpdate` generic Yjs validate/apply helper Document already uses (object-agnostic, unmodified) + per-workspace Rid allocation, inside `mutate()` → durable write completes → **only then** is the ack frame built and sent. Same persist-before-ack ordering as Document, proven the same way (real fault injection reusing Task 44's `store.persist` override hook, now exercised against the Database path too). Field add/rename require no database-specific server logic at all: AppFlowy-Web's own `dispatch.ts` performs them as ordinary Yjs CRDT mutations sent as a generic Update message — the backend only ever sees an opaque binary diff, exactly like a Document edit.

### Database creation (HTTP atomic-creation)
`POST /api/workspace/{id}/v2/page-view/database/default` → validates identity/shape → `createInitialDatabaseCollab()` builds the initial Yjs state → `store.createAtomicDatabasePage()` (mirrors `createAtomicDocumentPage` field-for-field: same `atomicCreationRequests` idempotency table, same rollback-on-throw pattern) writes two ordinary Folder-tree `store.pages` records (the sidebar container entry and its primary-view child, both required by the frontend's own post-creation validation) plus the new `databaseCollabDocuments` entry, all inside one `mutate()` call. `GET .../database/{id}/restore-state` (also new) always reports a fixed "no restore has ever happened" shape consistent with the Database object's own `collab_version` — restore itself is out of scope for Phase 1.

### DatabaseRow edit (WebSocket) — added Task 62
Client → WS frame (`collabType: 4`) → `server.js`'s new, additive DatabaseRow branch (inserted between the Database branch and the WorkspaceDatabase gate, touching neither) → `store.acceptDatabaseRowCollabUpdate()` → same `preparePageCollabUpdate` generic Yjs validate/apply helper Document/Database already use (object-agnostic, unmodified) + per-workspace Rid allocation, inside `mutate()` → durable write completes → **only then** is the ack frame built and sent. Same persist-before-ack ordering, proven the same way (real fault injection reusing Task 44/61's `store.persist` override hook, now exercised against the DatabaseRow path too). Cell writes require no row-specific server logic at all: AppFlowy-Web's own `dispatch/cell.ts` performs them as ordinary Yjs `Y.Map` mutations sent as a generic Update message — the backend only ever sees an opaque binary diff, exactly like a Document edit or a Database field rename.

### DatabaseRow creation (HTTP atomic-creation, with row-order insertion) — added Task 62
`POST /api/workspace/{id}/v2/database/{databaseId}/row/default` → validates identity/shape (including that `source_view_id` belongs to the target Database and that every `cells` key is a real field id of that Database) → `createInitialDatabaseRowCollab()` builds the initial Yjs state from the request's frozen `cells`/`height`/`visibility` → `store.createAtomicDatabaseRow()` performs, inside **one** `mutate()` call: (a) an idempotency check against a dedicated `atomicRowCreationRequests` table (separate from Document/Database's own `atomicCreationRequests`, so the two never cross-contaminate), (b) loading the parent Database's current Y.Doc, inserting `{id, height}` into the target view's `row_orders` at the requested position, capturing the resulting diff, (c) writing the new `databaseRowCollabDocuments` entry. Both the row and its row-order membership become durable together or not at all — this atomicity is required by AppFlowy-Web's own `assertMembership()`/`assertRow()` checks (`create-row.ts`), which is why row creation, unlike field add/rename, needed a dedicated REST endpoint rather than being purely a generic Yjs admission. The response's `database_update_v1` (a base64 Yjs diff) lets the creating client merge the new row-order membership into its own live Database doc without a second round trip; the frontend's optional `activation.row_encoded_collab_v1` hint is not implemented — the frontend's own fully-specified fallback (re-reading both objects via the existing single-object `GET .../collab/{id}?collab_type=` route, now also recognizing `collab_type=4`) is used instead.

### Version history / restore
`createPageCollabVersion` / `listPageCollabVersions` / `getPageCollabVersion` / `tombstonePageCollabVersion` / `restorePageCollabVersion` — additive structures (`pageCollabVersions`, `pageCollabRestoreEvents` in JSON; `collab_versions`, `restore_events` tables in Postgres via migration 005). Restore reuses the pre-existing `restore_id`/`RESTORE_GENERATION_MISMATCH` fencing (Task 45) verbatim — no new fencing mechanism was invented for it. Restore runs on the same single-writer boundary as ordinary updates in JSON mode, and as one `FOR UPDATE`-locked transaction with an optimistic-concurrency `WHERE generation=$current` guard in Postgres mode.

### CORS
`applyCorsHeaders` runs unconditionally before any auth logic; it sets `Access-Control-Allow-Origin` only to the literal matched allowlisted origin (never `*`, never combined with `Access-Control-Allow-Credentials`, which is never set at all — auth here is Bearer-token-only, so credentialed CORS was never needed).

## 3. Explicit risk/decision register

Each item below is labeled as instructed: **Verified architectural fact** / **Evidence-backed concern** / **Open design decision** / **Recommendation**.

### (1) Is the backend sufficiently separated from AppFlowy Cloud?
**Verified architectural fact** — for everything actually implemented (auth, workspace/page CRUD, document Yjs collaboration, version history, CORS), there is zero runtime dependency on GoTrue, MinIO, Redis, or any AppFlowy Cloud service; `server.js` is a from-scratch implementation.
**Evidence-backed concern** — this "separation" is proven only for the ~1/3 of AppFlowy-Web's surface that is implemented. The other 2/3 (sharing, database, files, search, AI, comments, notifications) isn't "independently implemented," it's simply absent — so no claim of independence can yet be made for those areas one way or the other, including whether AppFlowy-Web's own code for them could be made to work without reproducing some of AppFlowy Cloud's exact contract shapes (e.g. the GoTrue-shaped auth-refresh error handling found in `gotrue.ts`).

### (2) Can AppFlowy-Web remain the primary frontend?
**Verified architectural fact** — yes, demonstrated repeatedly end-to-end with real Playwright+Chromium sessions (Tasks 39, 40, 56, 57) for every feature currently built. **Recommendation**: preserve this direction; nothing found in this task suggests a blocker. The large remaining frontend surface (database/sharing/files/search/AI UI) is a reason to build backend support for it, not a reason to abandon the frontend.

### (3) Are JSON and Postgres storage behaviorally consistent?
**Evidence-backed concern, mostly positive** — for document collaboration and version history specifically, Task 49B and Task 56 produced real-Postgres-runtime parity evidence (disposable containers, not mocks), including fault-injection and concurrency scenarios mirrored from the JSON suite. **Open design decision/limitation**: this task did not exhaustively re-verify parity for every single route (e.g. favorites/trash Postgres parity was asserted by Task 53 but not independently re-run against a live Postgres database this task); treat full-surface parity as "believed consistent based on consistent evidence so far," not "exhaustively proven."

### (4) Is the collab architecture ready for multiple backend instances?
**Evidence-backed concern — no.** `cross-instance-replay` is explicitly, deliberately pending (Tasks 19, 46, 47, 58) because no second-instance evidence has ever been produced and the Rid allocator is per-process, per-workspace in-memory/DB-local state, not a shared sequencing authority. Protocol comments imply a Redis-stream design was once envisioned, but no server implementation of it exists anywhere in any checked-out repo.

### (5) Is the current document-state storage approach sufficient at scale?
**Evidence-backed concern.** The current-state representation itself is already minimal (one full Yjs state + state-vector pair per document, rewritten on each accepted update — Task 47 confirmed there is nothing to "compact" in that sense). The concern is unbounded **history** growth: Postgres's `collab_updates` table retains every raw update payload indefinitely (used only for dedup today), and the new `collab_versions`/`restore_events` tables have no retention/TTL/count cap. **Open design decision**: a retention policy (frontend already shows an `isPro`-gated hint of one) has never been made.

### (6) Are version history/restore safe under concurrent operations?
**Verified architectural fact, within tested scope** — duplicate restores, two concurrently-competing restores, and persistence-failure rollback were all proven safe by real fault-injection/concurrency fixtures in both JSON and real Postgres (Tasks 49A, 49B, 56). **Evidence-backed concern — not proven across instances or in a real multi-browser concurrent session** (only backend-level concurrency fixtures, not a live two-browser restore race).

### (7) Is the current authz model sufficient for real sharing/permissions?
**Evidence-backed concern — no.** Authorization today is workspace-membership-existence only; there is no per-document grant, no role-differentiated write permission confirmed in `server.js`'s checks, and the two sharing-adjacent endpoints are deliberate empty stubs. This is the single largest authz gap and must be designed (not just coded) before any real sharing feature is built, because it changes the authorization check on every existing document/workspace route.

### (8) Can database functionality be added without destabilizing document collaboration?
**Recommendation, with supporting evidence** — likely yes. The existing pattern (generic `store.*` method names shared across JSON/Postgres, `server.js` never branching on storage mode, version history added as a fully additive migration with zero changes to `collab_updates` or existing tables) suggests database functionality can be added as a new collab_type and a new additive schema without touching the document Yjs path. This is an **open design decision** on the exact row/field schema shape, not a known blocker.

### (9) Are file storage/templates designed for offline/self-hosted operation?
**Open design decision — nothing has been decided yet.** No storage backend (local disk vs. S3/MinIO-compatible) has been chosen. Upstream's template system is a self-hosted data model/API (`template.rs`), not a confirmed external marketplace URL — **this task explicitly could not confirm or deny a live "official template" service**, so building toward one would be inventing an unverified integration. The simplest de-risked path (bundling a static template set) is feasible but is a product decision, not yet made.

### (10) Which architectural decisions should be finalized before major feature work?
1. ~~Postgres migration advisory-lock fix~~ — **done, Task 59.** See `postgres-migration-lock.js` above and `docs/APPFLOWY_TASK59_REPORT.md`.
2. Retention policy for `collab_updates`/`collab_versions`/`restore_events`.
3. Authorization model shape for sharing (workspace role differentiation vs. per-document ACL vs. publish-link vs. all three).
4. File storage backend choice (local disk vs. S3-compatible) before any files/attachments work starts.
5. Whether multi-instance horizontal scaling is a near-term goal — this materially changes the Rid-allocator and WebSocket-broadcast design before database/sharing work is layered on top of the same collab machinery.
6. Whether to build any AI/search backend at all, and if so, with what explicit non-commercial dependency boundary (self-hosted keys only, graceful degradation if absent) — a product decision, not a technical one.

**No broad rewrite is recommended.** Every piece of evidence gathered this task is consistent with incremental extension of the existing `store.*`/migration/collab-admission pattern; the gaps found are missing features and a couple of concrete hardening defects, not a design flaw requiring architectural replacement.

## 4. Database architecture addendum (Task 60)

Task 60 performed a dedicated deep-dive discovery task on database functionality (full detail in `docs/DATABASE_ARCHITECTURE_AND_IMPLEMENTATION_PLAN.md`); the following items extend this document's risk/decision register using the same labeling convention as §3.

### (11) Can the existing collab/Rid/persist-before-ack pattern extend to database objects?
**Recommendation, with supporting evidence** — yes for database-metadata/views as a single additional collab object (upstream itself treats `CollabType::Database` as "just another type" on its generic sync/broadcast/persist pipeline, confirmed by reading real `AppFlowy-Collab`/`AppFlowy-Cloud` source — strong structural precedent). **Needs extension, not drop-in reuse**, once rows become independent collab objects too (upstream's confirmed model: one `CollabType::DatabaseRow` object per row) — the current `mutate()`/transaction boundary is scoped to one object at a time; N rows means N additional independently-synced objects, each needing Rid-stream and WS-subscription handling.

### (12) What is the cell-level conflict-resolution model?
**Verified architectural fact (upstream)** — upstream resolves concurrent same-cell edits via plain last-write-wins at whole-cell granularity (a flat `HashMap<String, Any>` map, overwritten wholesale on write; no per-cell CRDT, not even for rich-text cells). **Recommendation** — the independent backend does not need anything more sophisticated than this to match upstream fidelity; a Rid-ordered last-write-wins at the cell level is sufficient and upstream-equivalent.

### (13) Does the existing restore-generation-fencing mechanism (`restore_id`/`generation`, Task 45) extend to rows?
**Open design decision, with a recommendation** — not as-is. Recommend one generation counter per database that also fences child row writes (reuses the existing single-counter-per-mutate() pattern with minimal change) over a per-row counter (finer-grained but multiplies bookkeeping and requires a cascade-on-restore decision), unless per-row restore granularity becomes an explicit product requirement. **Recommendation, net-new (not an upstream-matching feature)**: extend fencing to cover concurrent row-delete-vs-in-flight-cell-edit (a `ROW_DELETED`/`ROW_GENERATION_MISMATCH`-style rejection, mirroring `RESTORE_GENERATION_MISMATCH`) — upstream's own behavior here is looser (orphan-and-leave, no fencing), so this would be a deliberate improvement beyond upstream, not a parity requirement.

### (14) Is the current WebSocket handler ready to accept database/row collab types?
**Evidence-backed concern — no, at Task 60's time of writing.** Direct code inspection (`server.js:1406-1407` and the collab-type allowlists at lines 512-513/701-702/753-754/763/801/559-573) confirmed there was no branch at all for `collabType` 1 (Database), 3 (Folder), or 4 (DatabaseRow) anywhere in the WebSocket admission path or the HTTP full-sync-batch per-item gate — only 0 (Document) and 2 (WorkspaceDatabase, placeholder-only) were handled.

**Update (Task 61): `collabType=1` (Database) is now handled** — a new, additive WS branch (inserted between the Document branch and the WorkspaceDatabase gate, neither touched) mirrors the Document branch exactly, and the full existing 38/38 regression plus 13 new Database-specific tests confirm it does not weaken the already-proven Document path. **`collabType=3` (Folder) and `collabType=4` (DatabaseRow) remain unhandled** — Folder real-time sync and row objects are both still out of scope (rows explicitly so, per Task 61's brief; Folder real-time sync was never in Task 61's scope at all, since Folder-tree writes happen server-side during atomic creation, not via client WS admission, for every Phase-1 workflow traced). The HTTP full-sync-batch per-item gate (lines noted above) was **deliberately left unextended for Database** — confirmed this task that AppFlowy-Web's `readCollabStates()` (the function actually used during Database creation-verification) calls the single-object collab-read route, not the full-sync-batch route, so extending the batch route was not required for Phase 1's workflow; whether a later phase's offline-reconnect-with-pending-edits scenario needs it is unassessed.

**Update (Task 62): `collabType=4` (DatabaseRow) is now also handled** — a new, additive WS branch (inserted between the Database branch and the WorkspaceDatabase gate, neither touched) mirrors the Database branch exactly, and the full existing regression (38/38 Document + 13/13 Database) plus 11 new DatabaseRow-specific tests confirm it does not weaken either already-proven path. **`collabType=3` (Folder) remains the only unhandled value** — Folder real-time sync was never in scope for any database-related task, for the same reason noted above (Folder-tree writes happen server-side during atomic creation). The HTTP full-sync-batch per-item gate was again **deliberately left unextended for DatabaseRow**, for the identical reason Task 61 gave for Database: `readCollabStates()` uses the single-object read route exclusively, confirmed again by this task's own source trace and by the real browser's own network log.

### (15) Does a database-level version-history/restore feature have upstream precedent?
**Evidence-backed concern — no confirmed upstream precedent found.** Neither `collab-database`'s own tests nor AppFlowy-Cloud's history-adjacent code showed a database-scoped analogue of the independent backend's own document version-history feature. The frontend's `database-history-api.ts`/blob-diff contract (`databaseId/history`, `databaseId/blob/diff`) is frontend-declared with no located server-side upstream implementation. **Recommendation**: if built, extend the existing per-object tombstone-snapshot-restore pattern (Tasks 49A/49B/57) to the Database collab object directly (same routes, new `collab_type` value) rather than inventing a new mechanism or attempting to reverse-engineer a nonexistent upstream contract.

### (16) Which new architectural decisions does database work add to item (10)'s list?
In addition to the six items `ARCHITECTURE_OVERVIEW.md` §3(10) already tracked: (a) how to treat the frontend's `FieldType` values 15-19 (Rollup/CreatedBy/LastEditedBy/Person/Formula), which have no upstream Rust-side counterpart at all (re-confirmed independently by two separate research passes this task); (b) whether Gallery/Form/Timeline/Chart/List/Feed database views (frontend-only concepts with no confirmed upstream server-side `DatabaseLayout` analog beyond Grid/Board/Calendar) are ever in scope as backend-original extensions; (c) per-row vs. per-database generation-fencing granularity (recommended: per-database, per (13) above); (d) whether database-level version history is wanted at all given no upstream precedent exists for it; (e) DateTime filtering/display timezone convention, since upstream's own convention could not be determined from available source (recommend UTC-stored/client-local-display as a new, explicit decision, not a discovered fact). Full detail and rationale for each: `docs/DATABASE_ARCHITECTURE_AND_IMPLEMENTATION_PLAN.md` §11. **None of (a)-(e) were resolved by Task 61** — Phase 1 (§5 below) deliberately only ever creates/edits `RichText` (0) fields and the Grid layout, so none of these decisions were forced; they remain open for Phase 2+.

## 5. Phase 1 implementation addendum (Task 61)

Task 60 §4 above was written entirely from discovery/design-doc evidence (no code existed yet). Task 61 implemented Phase 1 and real-browser-verified it; the items below record what the actual implementation revealed, using the same Verified/Evidence-backed/Open/Recommendation labels.

### (17) Was the "generic Yjs admission path extends to Database objects" prediction (item 11 above) correct?
**Verified architectural fact.** The Database WS branch is a near-literal structural copy of the Document branch (same `syncRequest`/`update`/`awarenessUpdate` handling, same persist-before-ack ordering via `mutate()`, same `preparePageCollabUpdate` helper reused unmodified). No database-specific merge/validation logic was needed anywhere. This also mechanically confirms item (12)'s last-write-wins-is-sufficient prediction, since the backend never inspects cell/field semantics at all — it only ever sees and applies an opaque binary Yjs diff.

### (18) Does the Folder-tree (`view` route) generalize safely to non-Document, non-space pages?
**Evidence-backed concern, resolved this task.** Before Task 61, the shared `GET .../view/{id}` route's "page" branch hardcoded `layout: 0`/`extra: null`/`children: []` for any page target — safe only because no non-Document page had ever existed to expose the gap. Task 61's Database container/view pages are the first `store.pages` records that need real `layout`/`extra`/children surfaced through this route. Fixed additively (`page.layout ?? 0`, `page.extra ?? null`, children computed for any page target using the same code already used for spaces) and proven safe for the pre-existing Document case by the full 38/38 regression (Document pages never set `.layout`, so the fallback is a no-op for them) — not just by inspection.

### (19) Is the existing object-permission endpoint (`/collab/{id}/permission`) actually scoped to "Document permission," or something broader?
**Evidence-backed concern, found only via real-browser verification, not inferable from the REST contract alone.** AppFlowy-Web's own `permissionProbe.ts` design treats this one endpoint as "permission for workspace folder view X" generically — Document is only the *default* `collabType` tag for any non-Database view, including spaces, not a hard requirement that the target be a Document collab object. The pre-existing implementation only ever recognized real Document pages, so a space id (needed to show the sidebar's only non-Document-layout creation entry point) or a Database id (needed for the Grid view's own field-menu UI, which probes with `collabType=1`) both 404'd/400'd, silently hiding UI controls with no visible error. **Recommendation for future similar work**: any UI control gated behind a permission probe should be exercised in a real browser before being assumed reachable from REST/WS contract correctness alone — this is now the second time in this project's history (after Task 51's CORS discovery) that a real-browser pass found a blocking defect invisible to contract-level testing.

### (20) What does Task 61 add to item (10)'s decision list?
Nothing new is *required* before Phase 1b/2 — Task 61 deliberately avoided forcing any of items (a)-(e) in (16) above. One new, low-urgency item: whether `GET /api/workspace/{id}/database` (the workspace-wide listing stub) and `POST .../database/{id}/blob/diff` need real implementations before Phase 4 (relations, which the architecture plan already flags as likely needing a database picker) — not assessed, flagged for whoever picks up Phase 4.

## 6. Minimum viable DatabaseRow lifecycle addendum (Task 62)

§5 above (Task 61) was written once Phase 1 (the Database object itself) existed but before any row ever did. Task 62 implemented the minimum viable row lifecycle — creation, ordering, generic cell editing — and real-browser-verified it. The items below continue the same Verified/Evidence-backed/Open/Recommendation labeling.

### (21) Does row creation follow the "generic Yjs admission" pattern Task 61 established for Database edits?
**Verified architectural fact, with one important qualification.** Once a row exists, cell edits are a near-literal structural copy of the Database field-rename pattern (§(17) above) — no row-specific merge/validation logic needed anywhere in the WS admission path. **Row *creation* itself, however, does not follow this pattern** — it required a dedicated atomic REST endpoint (`POST .../v2/database/{databaseId}/row/default`), because AppFlowy-Web's own `createCloudRow()` requires a single server-adjudicated operation that both creates the row collab object and proves its membership in the parent Database's `row_orders` array (`assertMembership()`) before the client will treat the row as real. A plain two-step "POST to create the row, then send a generic Yjs update to add it to `row_orders`" would leave a window where the row exists but isn't yet a view member (or vice versa), which the frontend's own creation code explicitly guards against. `storage.js`'s `createAtomicDatabaseRow()` performs both inside one `mutate()` transaction specifically to close this window.

### (22) Is row ordering really per-view Database-doc state, as item (12)/(38) predicted, or does the DatabaseRow object own any ordering concept?
**Verified architectural fact.** The DatabaseRow Y.Doc has no ordering concept whatsoever — confirmed by direct inspection of its full Yjs shape (`types.ts` `YDatabaseRow`) and by this task's own test coverage (row creation never touches the row doc's own structure to express position). `row_orders` lives entirely on the parent Database's Y.Doc, per-view, exactly as the Task 60 upstream-architecture discovery predicted.

### (23) Does row deletion/unlink require any new backend code?
**Verified architectural fact — no.** Traced directly from `src/application/database-yjs/dispatch/row-lifecycle.ts`: soft-delete (tombstone `is_deleted:true`) and "remove from view" (delete the `row_orders` entry + clear local IndexedDB cache) are both ordinary Yjs mutations of the Database doc, already admitted by Task 61's `collabType=1` WS branch, unchanged by this task. The real frontend code **never** issues a server call to hard-delete a DatabaseRow collab object in any code path (confirmed by reading every row-deletion-adjacent dispatch hook, not just the obviously-named ones) — this resolves what Task 60 had flagged as an open question (brief §D) with positive evidence, not caution-based deferral.

### (24) Is the row-detail page relationship (Task 60's flagged-unverified item) now confirmed?
**Verified architectural fact.** A row's detail/"peek" page, when it has one, is a separate `CollabType.Document` object with a deterministic id (`uuidv5('document_id', rowId)`, confirmed against `row-template-graph.ts` and the matching `metaIdFromRowId()` derivation in `const.ts`), created **lazily** — the `DefaultRowRequest` wire contract this task implements carries no document-content or document-id field at all, confirming plain row creation never touches it. This task does not create, open, or manage this object; the existing Document implementation (Task 35/36+) was not modified, and did not need to be.

## 7. PostgreSQL parity addendum (Task 63)

### (26) Does the generic Yjs admission/RID/dedup pattern (items 11/17/21) extend to PostgreSQL the same way it did to JSON?
**Verified architectural fact.** A single new, narrow class, `PostgresGenericObjectCollabRepository` (`postgres-collab-repository.js`), implements `load`/`acceptUpdate` once and backs both the Database and DatabaseRow Postgres repositories, reusing `preparePageCollabUpdate` and the exported `allocateMessageId` verbatim — no second RID allocator, no second dedup mechanism, no second update-validation implementation exists anywhere. ### (27) Was Postgres-mode Database creation actually reachable before this task, given migration 003's `pages.parent_view_id` foreign key?
**Evidence-backed concern, resolved this task — no, it was not reachable.** Migration 003 (`ALTER TABLE pages ADD COLUMN parent_view_id uuid REFERENCES spaces(id)`) only ever allowed a page's parent to be a space. ### (28) Is the atomic row-creation transaction's concurrency/rollback behavior equivalent between JSON and Postgres?
**Verified architectural fact, with real evidence, not just structural analogy.** The Postgres transaction (idempotency claim via unique-index-conflict-as-mutex → `FOR UPDATE` lock on the parent Database row only → Yjs mutation → row insert → parent-state update → idempotency-receipt fill-in → commit) was proven via real fault injection at six checkpoints to roll back completely with no partial state at any of them, and under genuine concurrency (two independent Postgres connections) to lose nothing and never duplicate for independent rows, identical-request-id races, and conflicting-request-id races alike. ### (29) Does this backend's real-time collaboration model actually broadcast content updates to other connected peers, as items in the brief for this task assumed?
**Evidence-backed concern, correcting an assumption — no.** Direct trace of every `collabType` branch in `server.js` (0/Document, 1/Database, 4/DatabaseRow) shows each `update`-admission branch's response helper (`sendDocumentFrame`/`sendDatabaseFrame`/`sendRowFrame`) writes back only to the sender's own socket. ## 9. Task 65 addendum — real-time collaboration architecture, investigated rigorously and root-caused (investigation only, no implementation — awaiting approval)

Item (29) above (Task 63's finding that no content update of any collab type broadcasts to other already-connected peers) was the explicit subject of Task 65, a dedicated, read-only architecture investigation. Full detail: `docs/TASK65_UPSTREAM_COLLABORATION_ARCHITECTURE_AUDIT.md` (Stage 1), `docs/TASK65_UPSTREAM_VS_INDEPENDENT_BACKEND_GAP_ANALYSIS.md` (Stage 2/3), `docs/TASK65_REALTIME_COLLABORATION_ARCHITECTURE_DECISION.md` (Stage 4/5, the decision). Summary below; do not re-derive these findings from scratch in a future task.

### (35) Is item (29)'s finding ("no content broadcast exists") actually the right level of description for upstream's own architecture, or does upstream do something more sophisticated that this backend is missing a whole mechanism for?
**Evidence-backed answer, traced to the function level across BOTH of upstream's two parallel realtime implementations — no, it is not more sophisticated in kind, only in deployment scope.** `AppFlowy-Cloud/services/appflowy-collaborate` ships a legacy per-collab-object "group" design (`group/*`/`rt_server.rs`, routed at `/ws/v1`) and the current workspace-scoped actor design (`ws2/actors/*`/`collab/collab_manager.rs`, routed at `/ws/v2/{workspaceId}` — the exact path AppFlowy-Web's real client and this backend both use). Both reduce to the same idea: a maintained, live roster of currently-connected sessions/subscribers (per-object in the legacy design, per-workspace in the live one) is iterated, minus the origin, and pushed to directly whenever an accepted update becomes visible. Upstream mediates this through Redis specifically because it targets horizontal multi-instance scale-out (any process can accept a write; any process's roster must learn about it) — a requirement this backend does not currently have or claim. Within a single process, this backend's own flat `websocketPeers` set, already filtered-and-iterated correctly for `awarenessUpdate`, is a complete, correct substitute for the same idea. No new infrastructure concept (message broker, collaboration-group abstraction, pub/sub) is missing in kind — only its application to one more message type.

### (36) Did this task find upstream's live (v2) protocol to be stronger or weaker than this backend's in any dimension, correcting any prior assumption that upstream is simply "more correct"?
**Evidence-backed, previously undocumented finding — weaker in one specific, important dimension.** Upstream's live v2 protocol sends **no acknowledgement at all** to the client that submitted an update (confirmed: no CollabAck-equivalent message type exists in the current protobuf schema used by `/ws/v2`), and its long-term durability (Postgres-backed snapshot) is asynchronous and decoupled from the moment an update becomes visible to other peers — only "written to a Redis stream" is guaranteed by that point, which is not itself guaranteed-durable unless Redis's own persistence is separately configured. This backend's persist-before-ack design (proven by fault injection across Tasks 44/61/62) is strictly stronger in this respect. This finding should prevent any future task from assuming "adopt more of upstream's behavior" is automatically a durability improvement — it is not, for this specific dimension.

### (37) What is the recommended fix, and why was adopting upstream's realtime service itself rejected again, having already been rejected once in Task 60.5?
**Re-examined with new evidence, not merely re-cited.** This task traced the LIVE v2 stack in addition to the legacy stack Task 60.5 had examined, and found it equally hard-coupled to Redis (not optional — it is the sole mechanism by which even the sender's own write becomes visible to anyone) and to AppFlowy-Cloud's own auth/workspace/permission schema (`CollabAccessControl`, `af_workspace`-shaped checks at every broadcast send). The recommendation (Option B in the decision document) is instead to extend this backend's own already-working, already-tested awareness-relay pattern (filtered scan of `websocketPeers`, skip origin) to the `Update` message path for all three collab types — zero new infrastructure, zero protocol change (the frame shape needed is identical to this backend's existing self-ack frame and to upstream's own broadcast frame), zero frontend change (AppFlowy-Web's `handleUpdate` already applies any incoming `Update` frame for an open object unconditionally, confirmed by direct source reading).

### (38) Is any implementation approved or started as a result of this task?
**No.** Per Task 65's own explicit, mandatory stop condition, this was an investigation-and-decision task only. The decision document (`docs/TASK65_REALTIME_COLLABORATION_ARCHITECTURE_DECISION.md`) is awaiting approval. No source file in either repo was modified by this task.

## 13. Task 69 addendum — Playwright browser-automation architecture: the `ViewModal` dual-render is the root cause of three tasks' independent navigation failures

### (51) Is AppFlowy-Web's `ViewModal` a genuinely separate rendering path, or was the "sticky header intercepts clicks" symptom actually several different root causes being misread as one?

**Not conclusively, and not fixed here (out of this task's scope either way).** A real user's own pointer click (unlike Playwright's actionability-gated click) DOES physically land on the modal's backdrop and closes it via its own `onClose` handler — so a real user experiences, at worst, a "first click doesn't do what I expected, second click does" UX rough edge, not a hard block. **No.** The existing contract (state-vector reconciliation on SyncRequest + content-digest dedup on Update admission + durable persist-before-ack + per-connection/per-frame CURRENT-auth-state checks from Task 67) was verified sufficient for every scenario in the task brief. No new reconnection state machine, no new idempotency key scheme, no new retry/backoff logic was added to the backend.

### (55) Task 70 — does the live-render finding change anything about the backend's own fan-out/persistence contract?

**No.** Task 70 (`docs/TASK70_HISTORICAL_COLLABORATION_ACCEPTANCE_REPORT.md`) ran all three historical workstreams' browser acceptance scenarios and isolated a specific, reproducible finding: an already-open SECOND browser context's editor does not always visibly re-render a remote body edit on its first live push after opening, while the identical content is reliably available via a normal reload immediately afterwards (a load-time fetch, not a live push), and live delivery was observed to succeed later in the same session after prior activity. ### (56) Task 70 — did test-harness state-sharing assumptions hold under Playwright's own defaults?

**Not initially, and this is a generalizable finding for future multi-scenario Playwright suites in this repo.** Playwright restarts ("recycles") its worker process — re-running that file's `beforeAll` from scratch — after ANY test in the file fails, which silently invalidates module-level state (e.g. a document id or marker set by an earlier test) that a LATER test in the same file expects to still exist, without raising any error about it (the later test simply sees `undefined`/a fresh environment). A deliberately-chained scenario design (scenario 2 depends on content scenario 1 wrote) must either avoid ANY hard-failing assertion in an earlier scenario that a later one depends on (recording a known-blocked finding as a non-fatal annotation instead), or persist the needed state somewhere that survives a worker restart (e.g. a file), or accept that a failure anywhere in the chain invalidates everything after it. This was confirmed empirically (distinct process PIDs logged across `beforeAll` re-invocations), not assumed from documentation.

## 14. Task 71 addendum — the cold-start live-render gap was a client-side WebSocket connection-binding race, not a backend or Yjs/editor-binding defect

Task 71 was a dedicated investigation-and-fix task for the specific gap Tasks 66/68/69/70 each independently observed (a freshly-opened second browser context's first remote update not reliably rendering live). Full detail: `docs/TASK71_COLD_START_LIVE_RENDERING_REPORT.md`.

### (55) Is this backend's AppFlowy-Web-facing protocol (one `websocket.objectId` slot per connection) itself a defect?

**No -- it is correct, consistently-enforced behavior that this task's evidence depends on, not a bug.** `server.js`'s Document/Database/DatabaseRow WebSocket branches all require `websocket.objectId === <this message's object>` before accepting an `update` or `awarenessUpdate` frame, closing the socket (1008/1003) otherwise. This is a single field per connection, shared across every collab type a client multiplexes onto that one socket -- intentional, simple, and already relied upon elsewhere (e.g. Task 67's authorization checks are per-connection). The defect this task found is entirely that AppFlowy-Web's own client never kept its belief about "which object currently owns this connection's slot" in sync with reality before sending for a given object.

### (56) Where exactly did the defect live, and why did it look like a Yjs/editor-rendering problem?

**`AppFlowy-Web/src/components/ws/sync/useSyncContextLifecycle.ts`'s `context.emit` and `AppSyncLayer.tsx`'s persistent-outbox `send` callback -- the two places a local edit or awareness change ever reaches the wire.** It looked like a rendering problem because the SYMPTOM (receiver never shows the update without a reload) is downstream of the ACTUAL failure (sender's frame gets rejected and re-routed through a slow, no-fan-out HTTP path) by several steps; only live two-sided instrumentation (not static code reading) distinguished "receiver's Yjs/editor layer never got the data" from "receiver's Yjs/editor layer got the data but didn't render it" -- it was conclusively the former.

### (57) Does the fix change the WS wire protocol, RID allocation, or Task 66's fan-out ordering?

**No.** The fix re-sends the EXISTING `SyncRequest` message (via a refactored-but-behavior-identical `buildSyncRequestMessage`/`bindSyncContext`) immediately before a frame that depends on it, relying on ordinary WebSocket/TCP frame-ordering guarantees on the SAME connection -- no new message type, no round-trip wait, no backend change.

### (58) Is any backend change required or proposed?

**No.** One adjacent, non-actionable observation is recorded in the implementation report (§10): the HTTP `collab_full_sync_batch` endpoint's lack of a live peer fan-out is a pre-existing, intentional-looking "slow lane" design choice, not a newly-discovered defect, and is not touched.

## 15. Task 72 addendum — additional-view creation needed one new atomic-creation route, nothing else; view CONFIGURATION needed zero new architecture

Full detail: `docs/TASK72_DATABASE_VIEWS_DISCOVERY.md`, `docs/TASK72_DATABASE_VIEWS_IMPLEMENTATION_REPORT.md`.

### (59) Did database views require any new collab-protocol message, storage abstraction, or query engine?

**No.** Views are embedded substructures inside the SAME Database collab object (`collabType=1`) Task 61 already built real-time admission for — not separate collab objects (confirmed both from upstream source and from this backend's own `database-document.js` shape). A view's configuration (filters/sorts/groups/field_settings/field_orders/layout_settings) is just more keys inside that same Yjs doc, admitted by the exact same generic validate/persist/ack/fan-out code path as a field rename, with zero awareness of what the diff actually represents. This task added **one** new HTTP route (view CREATION) and zero new WS message types.

### (60) Why did view creation need a new route at all, if configuration needed nothing?

**Creation is identity/placement bookkeeping (a new Folder-tree page + a new entry in the Database doc's `views` map), which — like every other object creation in this backend — goes through the atomic-creation convention (idempotent HTTP POST, not a Yjs diff) rather than the ongoing-collaboration WS path.** This mirrors exactly how Task 61 needed `page-view/database/default` for the FIRST view/database even though ongoing field edits need nothing database-specific; Task 72's gap was that the SAME convention was never extended to a database's Nth view.

### (61) Did implementing this surface any real bug, or was it purely additive?

**One real client-side contract bug was found and fixed, found only by driving a real browser, not inferable from the HTTP contract or the frontend's own opt-in interop test alone**: AppFlowy-Web's atomic-creation journal validates the creation RECEIPT (not just the HTTP status) before treating a creation as complete, and requires several fields (`database_id`, `database_restore_id`, `view_ids`, `database_version`, `update_batch_id`, `database_update_v1`) this task's first implementation omitted — the same "diff update" receipt shape Task 62 already used for row creation, just not previously recognized as ALSO required for view creation specifically. Fixed by computing the real Yjs diff and returning it, mirroring Task 62's pattern. This is this task's own instance of Task 61's finding that "REST-contract-looks-right is not sufficient evidence" (§ earlier in this doc).

### (62) Is any backend change required for Form (DatabaseViewLayout.Form=7) views?

**Deliberately not implemented, not a gap left open by oversight.** Form views require a companion "Responses" Grid view materialized server-side with no stored cross-reference (confirmed from the frontend's own interop test and `create-default-view.ts`), which is form-builder/public-submission functionality — a distinct, larger feature than "view lifecycle + configuration." Rejected with a clear `400`, matching Task 61's own precedent for non-Grid layouts on a database's first view.

### (63) Is the view-tabs UI rendering gap (found, not fixed) a backend problem?

**No, confirmed not.** The backend's persisted state was independently verified correct (via a direct collab-read call from within the browser test session, not trusted from the creating client): exactly two views, correct independent `layout` values. The gap is entirely in which DOM elements AppFlowy-Web's `DatabaseViewTabs`/`DatabaseTabItem` components choose to render for a standalone database page in this checked-out build — investigated enough to rule out the one plausible backend-adjacent cause (a client-compatibility version banner, confirmed purely cosmetic by reading its own consumer code), not pursued further within this task's backend-focused budget. See the implementation report §10.
