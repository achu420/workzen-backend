## 2. Evidence-class discipline (how this and future checkpoints should cite evidence)

Four classes, always distinguished, never blended:

1. **Previously verified evidence** — a prior task already ran this and recorded the result; re-cite it, don't re-claim it as new.
2. **Newly executed this task** — actually run in the current session, with the exact command and result recorded.
3. **Static code inspection** — read the code, did not execute it. Never describe this as "tested" or "verified."
4. **Not assessed** — explicitly say so rather than silently omitting.

Task 58 ran classes 2 for `npm test` (38/38), `npm run test:offline-collab` (5/5), and `npm run test:collab-conformance` (6 passed/2 pending/5 resolved) — see `PROJECT_CHECKPOINT_TASK58.md` §3. It relied on class 1 for `npm run test:postgres` (last run same day, Tasks 56/57, 10/10) and for every browser-verification claim (last real session was Task 57, same day). It used class 3 extensively for the upstream-AppFlowy and AppFlowy-Web-frontend-inventory findings in `FEATURE_REGISTRY.md` §2-8. It used class 4 explicitly for items like exact Postgres parity of favorites/trash and the existence of an official template marketplace API.

## 3. Rules this project has already established and should keep enforcing

- A passing unit/integration test is never described as browser verification.
- Structural Postgres code inspection is never described as real database runtime verification — only an actual run against a live (even if disposable) Postgres instance counts.
- An HTTP 200 is never treated as "feature complete" — the sharing-view and database-catalog stubs both return 200 and are explicitly, repeatedly documented as non-functional placeholders, not completions.
- A "pending" conformance vector is never silently moved to "resolved" without a cited fixture (`test/collab-conformance.js`'s structure enforces this — each resolved vector carries a narrative + test-file citation).
- Fault injection (delayed/failed persistence hooks) is preferred over static tracing wherever a safety claim ("X never happens before Y") is being made — this is how `realtime-ack` was actually proven (Task 44), not inferred.

## 4. Regression requirements going forward

Any future task that touches `server.js`, `storage.js`, `postgres-storage.js`, `postgres-collab-repository.js`, `collab-protocol.js`, (added Task 61) `database-document.js`, or (added Task 62) `database-row-document.js` should, at minimum:
1. Run `npm test`, `npm run test:offline-collab`, `npm run test:collab-conformance` and report exact before/after counts (this project's established convention across all 61 prior tasks — never broken once). **Added Task 61**: if the change touches the Database collab path, also run `npm run test:database-collab`. **Added Task 62**: if the change touches the DatabaseRow collab path, also run `npm run test:database-row-collab`.
2. Run `npm run test:postgres` if the change touches Postgres-mode code, against a disposable, isolated, always-torn-down container — never the commercial stack's container, never a shared/production database.
3. Only claim browser verification after an actual Playwright (or equivalent) session against a real backend + real Vite dev server + the real AppFlowy-Web code, with console/network evidence captured.

## 5. Completion standard for a feature to be called "Complete" in `FEATURE_REGISTRY.md`

A feature earns the **Complete** label only when it has: backend implementation in both JSON and Postgres modes (or an explicit, documented reason one mode is N/A), automated test coverage for both modes where applicable, and real browser verification of the actual user-facing flow. Document version history/restore is the only major feature area that currently meets this full bar (Tasks 49A/49B/56/57 together). Document collaboration meets it for the single-instance case only — multi-instance is explicitly excluded from the "Complete" label pending `cross-instance-replay` resolution.

Any future acceptance criterion phrased as "reopen X" or "a second user opens X" should be read as requiring a *fresh* session/context specifically, not merely a reload of an already-warm one, and the two should be evidenced separately when they diverge (as they did here).

## 11. Task 65 addendum — an investigation-only task's evidence-class discipline, and re-running a prior task's own fixture as fresh evidence rather than citing it secondhand

Task 65 was explicitly investigation-and-architecture-decision only (no implementation permitted, per its own mandatory stop condition), which makes it a useful worked example of this document's evidence-class discipline (§1/§3/§7/§8/§9/§10) applied to a task that produces zero shippable code. Full detail: `docs/TASK65_REALTIME_COLLABORATION_ARCHITECTURE_DECISION.md`, `docs/TASK65_UPSTREAM_COLLABORATION_ARCHITECTURE_AUDIT.md`, `docs/TASK65_UPSTREAM_VS_INDEPENDENT_BACKEND_GAP_ANALYSIS.md`.

**A new discipline point this task adds**: when a task's job is to diagnose a symptom a *prior* task already found (here, Task 63's "no content broadcast" observation), the correct evidentiary move is not to cite the prior task's report as settled fact, but to **re-run the prior task's own fixture fresh, this task, and read its live output** — this task re-ran `test:postgres`'s `postgres-database-multiclient.test.js` fixture specifically and cited its fresh log lines ("peer received NOTHING" for both a REST row creation and an ordinary WS cell update) as this task's own live runtime observation, not as an inherited claim. This matters because an investigation task that only re-reads static code and a prior task's prose risks laundering a stale or subtly-wrong historical claim into a new decision document as if it were freshly verified; re-running the exact fixture costs almost nothing and removes that risk entirely.

**A second new discipline point**: this task found that this environment's shell state does not persist environment-variable `export`s across separate tool-call invocations, which caused the entire `test:postgres`/`test:parity` suites (43+2 tests) to silently report as `SKIP` (not fail) on the first attempt, because `RUN_POSTGRES_TESTS=1` and `DATABASE_URL` must both be true in the *same* shell invocation as the test command for the suites' own `skip: !configured` guards to pass. The correct response, demonstrated here, is to notice that 0 pass + 0 fail + N skip is not the documented baseline (which is N pass), re-derive the exact `DATABASE_URL` prior tasks used (found in `docs/APPFLOWY_TASK61_REPORT.md`'s own evidence table, not guessed), and re-run with both variables exported in one combined shell command — not to report a false "baseline regression" or silently accept a lower bar. This generalizes to any future task needing to invoke the Postgres suites in a fresh shell session in this environment.

**A worked example of root-causing a failing real-browser check with server-side ground truth, rather than guessing at UI timing**: an early real-browser iteration of the Document live-update scenario failed at its very first baseline check (member sees owner's already-typed text) with the member's DOM showing a genuinely empty editor (confirmed via a diagnostic DOM dump, not assumed). This is the generalizable lesson: when a real-browser assertion about CROSS-CLIENT delivery fails, check server-side ground truth FIRST to rule out "it was never sent" before assuming "it was sent but not delivered" (the actual thing under test).

## 16. Task 70 addendum — all three historical workstreams' outstanding browser scenarios run in one coordinated effort; a Playwright test-isolation gotcha and a render-vs-reload content-delivery finding, both root-caused rather than papered over

Task 70 built `test/e2e/historical-collaboration-acceptance.spec.ts` (Task 66/67/68 workstreams, each its own `test.describe` with its own disposable environment) on Task 69's infrastructure. Full detail: `docs/TASK70_HISTORICAL_COLLABORATION_ACCEPTANCE_REPORT.md`.

**A new discipline point: a chained multi-scenario Playwright design must account for worker-recycle-on-failure, or it silently breaks.** Playwright discards and restarts its worker process (re-running that file's `beforeAll`) after ANY failing test in the file — confirmed empirically here via distinct logged process PIDs across `beforeAll` re-invocations, not assumed from documentation. **A render-vs-reload content-delivery finding, isolated with a specific, decisive diagnostic rather than left as an unexplained flake**: across every one of 5 full-suite runs, a freshly-opened SECOND browser context's editor consistently failed to visibly re-render a remote body edit on its first live push after opening (confirmed via a DOM dump proving the CORRECT document instance was mounted, with placeholder-only content — ruling out "wrong element matched"), while the identical content was reliably available via an immediate reload (a load-time fetch, not a live push) in every run. `page.bringToFront()` was tried and ruled out headless-tab timer throttling as the cause. Later-stage checks within the SAME two contexts (after at least one prior reload/round of activity) observed live delivery succeed in multiple runs, suggesting a first-push/"cold" render race rather than a universal block. **A reused-helper semantics gotcha, found via a genuine regression failure, not hypothesized**: the existing `typeIntoDocumentBody` helper (Task 69) intentionally replaces the ENTIRE document body on every call (Select-All + Backspace, then type). Scenarios needing multiple markers to coexist in one document (continued collaboration, pre-/post-restart convergence) silently had earlier markers wiped when a later scenario reused this helper on the same document.
