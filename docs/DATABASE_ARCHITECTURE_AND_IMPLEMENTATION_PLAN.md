# Database architecture and implementation plan (Task 60)

Read-only discovery/design document. No application code, schema, or API behavior was changed to produce this. All findings below are classified by evidence class, consistently: **confirmed (static code inspection)**, **confirmed (upstream source inspection)**, **previously verified evidence** (automated tests re-run this task), or **recommendation** (this document's own design judgment, explicitly not upstream fact and not yet implemented). Do not read any "recommendation" item as already decided or built.

This document builds on, and does not replace, `MASTER_FEATURE_ROADMAP.md`'s Milestone 2 sketch and `FEATURE_REGISTRY.md` §2's gap table — both were written at a coarser grain in Task 58. This task re-investigated database functionality in much greater depth (three parallel deep-dive investigations: frontend, upstream Rust/collab data model, upstream collaboration protocol) and the findings below are more granular and in some places correct/sharpen Task 58's claims (see §1 "Corrections to prior findings").

## 0. Executive summary

AppFlowy-Web has a **deep, genuinely-wired, desktop-parity-grade** database implementation on the frontend — not UI scaffolding. It is wired almost entirely to a **Yjs collaborative-sync substrate** (WebSocket-first, HTTP-batch-fallback, IndexedDB offline outbox), not to a conventional CRUD REST API. The independent backend implements **zero** of the database-specific collab types or routes: it accepts and broadcasts only `CollabType::Document` (0) and a placeholder `CollabType::WorkspaceDatabase` (2) catalog object; `CollabType::Database` (1), `CollabType::DatabaseRow` (4), and `CollabType::Folder` (3) are entirely unhandled at the WebSocket layer, and at least 15 distinct frontend-declared REST/atomic-creation endpoints (database/view/row creation, CSV import, row-document duplication, database history/blob-diff, orphaned-view materialization) have no backend route at all — a materially larger gap than Task 58's single-stub framing suggested.

Upstream AppFlowy's actual database architecture (confirmed by reading real `AppFlowy-Collab`/`AppFlowy-Cloud`/`AppFlowy` source, not inferred) is a **graph of linked Yjs collab objects**, not one big document and not a relational schema: one `WorkspaceDatabase` catalog object per workspace; one `Database` object per database (fields + views + per-view row-order arrays, no row content); one independent `DatabaseRow` object per row (cells as a flat last-write-wins map, not per-field CRDTs); and, when a row's expandable detail body is actually written to, one more object reusing the plain `Document` collab type, with a UUIDv5-derived id. This is the single most load-bearing finding of this task: **cells are not individually-addressable CRDTs upstream** (no YText per cell, not even for rich-text fields) — conflict resolution at cell granularity is last-write-wins via ordinary Yjs `Map.set`, and row ordering is a per-view Yjs `Array` of `{row_id, height}` references. There is no native upstream Rollup field type, and no `created_by`/`last_edited_by` field type either (both re-confirmed absent this task, by two independent investigation passes).

**Recommended storage architecture: Option B (hybrid relational + collaborative), with upstream-compatible collab_type framing** — not pure Option A (fully relational) and not a byte-for-byte reproduction of Option C. The reasoning, detailed in §5, is that upstream's own design already uses relational-shaped lookups for most of what matters (field definitions, view settings, row order) layered over a thin collaborative sync envelope only where upstream itself puts one (database metadata+views as one synced object, each row as another synced object) — so a pure-relational design would diverge from the wire contract the frontend already speaks (its Yjs dispatch layer expects to read/write `YDatabase`/`YDoc` maps, not call a REST CRUD surface for 30 of the 35 operations investigated), while a byte-for-byte Option C would require reimplementing Yjs CRDT semantics the backend doesn't need (true multi-writer merge below cell granularity) for a self-hosted, typically-small-team deployment where the existing single-writer `mutate()`/transaction boundary already removes most of the race upstream's CRDT exists to solve.

**Recommended Phase 1 scope**: discovery is this document; the first *implementation* task (next task, not this one) should build the `Database` collab object (metadata + fields + views, scoped as one Yjs-syncable object per database, following upstream's `CollabType::Database=1` framing) in JSON+Postgres, wired through the existing `store.*` generic-method pattern, with real WebSocket admission for `collabType===1` added to `server.js`'s existing per-type gate — deliberately **not** rows/cells yet (Phase 3), and deliberately **not** Board/Calendar/Form view types yet (Phase 2 sub-scope, Grid only first). See §9 for the full phase breakdown.

**Top risks** (full register in §10): (1) cell/row data model compatibility with the frontend's existing Yjs dispatch layer — the frontend is pre-built to a specific `YDatabase` shape and will not degrade gracefully if the backend's Yjs state doesn't match that shape; (2) the WebSocket handler's current per-collabType allowlist is a hardcoded gate (`collabType !== 0`/`!== 2` checks) that must be extended carefully without weakening the existing Document path; (3) row-as-independent-collab-object multiplies the number of synced objects by row count, which stresses the existing per-object Rid/mutate() assumptions in ways not yet tested at scale; (4) relation fields (cross-database references) and rollup-adjacent aggregation have no clean upstream precedent to copy (relation is even explicitly filtered out of AppFlowy-Cloud's own REST row-detail API as unsupported); (5) authorization model is still workspace-membership-only — database-level and row-level authorization checks do not exist and must be added, not assumed inherited.

**Recommended first concrete implementation task** (next task, not this one): build the `Database` (collab_type 1) object — metadata/fields/views only, Grid layout only, JSON mode only — as a new, additive repository method set following the exact `store.*` pattern version history used, with the single acceptance bar: create a Grid database via the real frontend UI, add/rename fields, reload, and see the same fields persist. Defer rows, Postgres parity, and WS wiring to immediately-following sub-tasks per §9's phase breakdown. This differs from Milestone 2's Task 58-era framing (which treated "database functionality" as one undifferentiated blob) by sequencing Database-object-only first, since it is the smallest slice that lets the frontend's existing dispatch/view code start exercising real (not stubbed) backend state.

## 1. Corrections and sharpenings to prior task findings (Task 53/58)

- Task 58/53 framed the gap as "one honest-empty stub" (`GET /api/workspace/{id}/database`). This task found **at least 15 additional, entirely absent, frontend-declared endpoints** beyond that stub: atomic database/view/row creation (3 routes), legacy non-atomic database-view creation, row-document duplication, row-comment notification, database version history, database blob-diff (restore/compare), CSV import (create/upload/status/cancel — 3-4 routes), `orphaned-view` (the mechanism that materializes a row-detail page), and `upgrade-database-container`. None of these were previously enumerated in `FEATURE_REGISTRY.md` §2's table at this level of detail.
- Task 58 correctly identified that the frontend data layer is "Yjs-based," but did not previously establish, at the protocol level, that the backend's WebSocket handler has **no branch at all** for `collabType` 1 (Database), 3 (Folder), or 4 (DatabaseRow) — only 0 (Document) and 2 (WorkspaceDatabase placeholder) are handled (`server.js:1406-1407` and the collab-type allowlists at lines 512-513, 701-702, 753-754, 763, 801). This is a structural protocol gap, not just missing REST routes — even if every missing REST route were added, real-time sync for actual database/row content would still be silently dropped.
- Task 58 said upstream has "no native Rollup field type" based on the Rust `FieldType` enum. This task **re-confirms that independently** (absence checked against the actual enum values 0-19 the frontend's `FieldType` TypeScript enum tracks, AND against the absence of any `rollup_entities.rs`/rollup type-option file upstream) — but also found the **frontend's own `FieldType` enum includes `Rollup=16`, `CreatedBy=17`, `LastEditedBy=18`, and `Formula=19`** with substantial dedicated test coverage (`rollup-formula-combinations.test.ts`, `rollup-related-schema-sync.test.ts`), none of which correspond to anything in the upstream Rust enum (which tops out at 14, Media). This is a **newly identified frontend/upstream contract divergence**, not previously documented: the frontend has apparently moved ahead of (or diverged from) the specific upstream Rust revision pinned in this project's reference checkouts, and/or implements these as frontend-computed/derived fields with no server-side field-type counterpart. This must be resolved as an explicit decision (§11) before Phase 3, not assumed away.
- Task 58 said relation/rollup support is unconfirmed; this task confirms **Relation** has a real upstream field type (`FieldType::Relation=10`, type-option stores a target `database_id`, cell data is a list of related row ids) but is **explicltly excluded from AppFlowy-Cloud's own REST row-detail API** (`UNSUPPORTED_FIELD_TYPES = &[FieldType::Relation]`) — i.e. even upstream's own cloud server treats Relation as too awkward for its plain-JSON REST surface, which is useful precedent for scoping it out of early phases here too.

## 2. Part A — Frontend database implementation discovery

### 2.1 Headline finding
The "fully built UI and API-client code" characterization from Task 58 **understates** the frontend's depth (dispatch logic alone is ~5,200 lines across `dispatch.ts` plus modularized `dispatch/{row,cell,field,view,group,sort-filter,relation,row-lifecycle,calculation,new-row-cells}.ts`, with 100+ dedicated test files covering rollup/relation two-way-reciprocity/CSV-import/field-type-migration/filter-trees) but **overstates** how much of it is reachable via simple REST calls — only page/view lifecycle (create/duplicate/move/trash/favorite) and a handful of "atomic default creation" endpoints are plain REST; everything else is read/written as local Yjs state and synced via the generic collab full-sync-batch/WebSocket transport.

### 2.5 Row-detail-page mechanism (confirmed)

A database row's expandable detail page reuses the plain `Document` collab type, not a special row-document type. The row-document id is deterministically derived from the row id (same derivation convention upstream uses, see §3). It is materialized server-side as "an orphaned folder view whose id equals the row's document id," via `POST /api/workspace/{id}/orphaned-view` (`view-api.ts:196-210`, absent in backend) — this is what lets the row page be favorited/trashed through ordinary page-view routes once it exists. The content body itself is fetched/created via the separate `row-document` atomic-creation route. Both routes are currently absent; the row-detail feature is architecturally sound and fully coded on the frontend but depends on two backend routes that don't exist, plus WS support for `collabType=4` which also doesn't exist.

## 3. Part B — Upstream AppFlowy data model (confirmed by reading real pinned-revision source)

Source basis: `AppFlowy-Collab` at the exact revision pinned by both local checkouts' `Cargo.toml` (`4dfccef` / `e59260e524f33104b0ddcd6bb8f6218cad0f7e18`, functionally the same lineage), fetched directly since the crate is not vendored locally; plus local `AppFlowy-Cloud` and `AppFlowy/frontend/rust-lib` checkouts. The commercial reference repo (`AppFlowy-SelfHost-Commercial`) was checked and confirmed to contain **no source code at all** (deployment/ops docs only) — there is no commercial-only data-model divergence to flag because there is no data model there.

### 3.1 Database identity/structure (confirmed)
A "database" is an abstract id, decoupled from any single view: a per-workspace `WorkspaceDatabase` collab object (`collab-database/src/workspace_database/body.rs`) holds an array of `DatabaseMeta{database_id, created_at, linked_views}` — one database can be linked from N folder views. The database's own content (fields, views, row-order-only) lives in a separate `Database` collab object (`collab-database/src/database.rs`), id = the database's own UUID. No dedicated name/icon/config lives on the Database object itself — name/icon live on the linked Folder View; `AFDatabase` DTO (AppFlowy-Cloud) is just `{id, views: Vec<FolderViewMinimal>}`. Deletion is via trashing the linked folder view(s), not a dedicated database-delete flag — no tombstone struct was found on the Database object itself.

### 3.2 View structure (confirmed)
Views are **not** separate collab objects — they are embedded substructures inside the Database collab doc (`DatabaseBody`'s `"views"` map, `database.rs:71`), confirmed explicitly by an AppFlowy comment: "there are no physical collab object for the database view." `DatabaseLayout` enum: `Grid=0, Board=1, Calendar=2` (upstream has no Gallery/Form/Timeline/Chart/List/Feed server-side layout value — those are frontend-only extensions per §1). Each view carries its own `row_orders: Vec<RowOrder>` (filters/sorts/groups/field-settings/layout-settings are all per-view, keyed by `view_id`, not per-database) — confirmed via `DatabaseViewSettingPB{layout_type, layout_setting, filters, group_settings, sorts, field_settings}` and per-`(view_id, field_id)`-scoped `FieldSettingsPB{visibility, width, wrap_cell_content}`. One view is designated the database's "inline view" (the default/primary embedded view). Confirmed collab-side type names via import statements (defs not locally readable): `GroupSettingMap`, `LayoutSettings` (map keyed by `DatabaseLayout`→`LayoutSetting`), `FieldSettingsByFieldIdMap`. `FilterMap`/`SortMap` exact names not independently confirmed (plausible by analogy with `GroupSettingMap`, not verified). `OrderObjectPosition{Start, End, Before(id), After(id)}` is used uniformly for both row and field ordering.

### 3.3 Row structure (confirmed — most important finding for this task)
**Rows are independently collaborative Yjs objects** (`CollabType::DatabaseRow=4`), not entries inside the Database doc. Each row gets its own `Collab::new_with_options(object_id=row_uuid)`, wrapped by `DatabaseRowBody`. The Database doc's view-scoped `RowOrder{id, height}` is a *reference* only — it never holds cell content. Row fields: `id (UUID), height, visibility, created_at, modified_at, cells (HashMap<field_id, Cell>), database_id`. No tombstone struct for rows was found — removal from a view's `row_orders` array (via `remove_row_order`) is the only deletion mechanism observed at the collab-database layer; whether/when an orphaned row's own collab object is ever hard-deleted was **not determinable** from available source (a generic `delete_collab`/soft-delete-via-`deleted_at` path exists at the AppFlowy-Cloud storage layer and is usable for any collab type, but no call site tying row-unlink to row-hard-delete was confirmed).

Row "detail page": the expandable body is a **separate `CollabType::Document` object** (the same type as an ordinary page), whose id is **deterministically derived** from the row's own UUID via `meta_id_from_row_id(row_id, RowMetaKey::DocumentId)` (a UUIDv5-style derivation) — confirmed from both `collab-database` usage sites and AppFlowy-Cloud's `check_if_row_document_collab_exists()`, which independently recomputes the same derived id and checks it against the generic `af_collab` table, proving the row-detail doc is stored and fetched through the exact same generic collab-storage path as any other Document. `RowMeta{icon_url, is_document_empty, attachment_count, cover}` and `RowCover::{ColorCover, FileCover, AssetCover, GradientCover}` exist as row-level (not cell-level) metadata.

Upstream has no evidence of an integrated database-level version-history/restore feature analogous to this backend's existing document version history (not found in `collab-database` tests or AppFlowy-Cloud's history crate for Database/DatabaseRow object ids specifically) — database "history"/"restore" in the frontend's own API contract (`database-history-api.ts`, blob-diff) is a frontend-declared contract with **no confirmed upstream server implementation located**; treat this as **unknown**, not as a confirmed upstream feature to replicate.

### 3.4 Property/field structure (confirmed)
`Field{id, name, icon, field_type: i64, is_primary: bool, type_options: HashMap<String, TypeOptionData>}`. `TypeOptionData = HashMap<String, yrs::Any>` (confirmed directly) — a flat per-field-type config map; some types (SingleSelect/MultiSelect/Media) store their richer config (e.g. the options list) as one JSON-stringified blob inside a single map entry rather than as nested Yjs structures — this is an important storage-shape detail for any reimplementation to match if wire-level collab compatibility with a real AppFlowy desktop/mobile client is ever required. No "required/optional" flag exists on Field — only an implicit primary/title field (`is_primary`). Type conversion (e.g. Checkbox→SingleSelect) is field-type-pair-specific custom logic via a `TypeOptionTransform` trait, not a generic coercion.

### 3.5 Cell structure (confirmed)
Serialization/validation/update is delegated entirely to per-field-type reader/writer objects (`TypeOptionCellReader`/`TypeOptionCellWriter`), not a generic cell schema. AppFlowy-Cloud's REST surface represents cells as plain JSON (`HashMap<String, serde_json::Value>`, keyed by field **name** on read, field **id** on write — an asymmetry worth replicating carefully if ever matched). CreatedTime/LastEditedTime values are **not necessarily stored** — when absent, the server synthesizes them live from the row's own `created_at`/`modified_at` timestamps, confirming these are row-level, not cell-level, source of truth. Cell writes for the REST row-upsert path are a partial/per-field merge into the existing row, not a full-row replace. Three distinct serializations exist for "the same" cell value depending on transport (Dart/Rust FFI binary ProtoBuf, Yjs/collab map, REST JSON) — do not conflate them when designing a wire contract.

## 4. Part C — Database collaboration architecture

All eleven required questions, answered with confirmed-vs-not-determinable labeling, followed by a clearly separated recommendation section.

1. **Is database metadata collaborative Yjs or relational/REST?** Confirmed (upstream source) — Yjs. `Database.collab`/`DatabaseBody` is intrinsically a Yjs CRDT document (`collab-entity`'s `CollabType::Database.validate_require_data()` requires a `DATABASE` map); there is no relational/REST metadata path upstream.
2. **Are views collaborative Yjs, same doc as metadata or separate?** Confirmed (upstream source) — same doc as database metadata (not a separate doc, not the WorkspaceDatabase catalog doc). `database.rs` holds `"fields"` and `"views"` as sibling keys under one `Collab`.
3. **Are rows independent Yjs objects or part of one shared structure?** Confirmed (upstream source) — independent. `CollabType::DatabaseRow=4`, one per row, separately encoded/synced; `Database::encode_database_collabs()` explicitly produces N+1 distinct encoded collabs (1 database doc + N row docs) on export.
4. **Do cells use Yjs CRDT types or plain serialized values in a map?** Confirmed (upstream source) — plain serialized values in a flat `HashMap<String, Any>` (`Cell` type alias), written via whole-map `fill()`/overwrite, not per-field CRDT types. Even RichText-typed cells store a flat string scalar, not a YText.
5. **Are row-detail pages separate Yjs docs reusing the Document type?** Confirmed (upstream source) — yes, exactly the same `CollabType::Document` as ordinary pages, id deterministically derived via UUIDv5 from the row id, lazily created only when first written to.
6. **Same WS protocol/collab_type framing as documents? Numeric values?** Confirmed (upstream source), exact: `Document=0, Database=1, WorkspaceDatabase=2, Folder=3, DatabaseRow=4, UserAwareness=5, Unknown=6`. One generic WS scope (`/ws/v2/{workspace_id}`) and one generic `InitSync`/`ClientUpdateSync` message envelope handle every collab_type; server-side fan-out (`CollabGroup`/`CollabPersister`) is generic across types, with the only type-specific branch found being a Document-only AI-indexing/awareness gate — not a different sync/broadcast code path.
7. **Is row ordering collaborative CRDT state or plain backend metadata?** Confirmed (upstream source) — collaborative: a per-view Yjs `Array` of `RowOrder{id, height}`, with native Yjs insert/remove/move-at-index semantics, not a plain integer `sort_key` column.
8. **How are concurrent same-cell edits reconciled?** Confirmed (upstream source) — last-write-wins at the whole-cell granularity via Yjs `Map` set semantics (higher Lamport-clock/client-id wins deterministically on every replica); no field-type-aware structured merge.
9. **How does row deletion/restoration work; interaction with undo/history?** Confirmed (upstream source), partial — row removal from a view is an "unlink" (strip the `RowOrder` reference), not a doc delete; the row's own collab object is left orphaned (not confirmed whether it is ever hard-deleted — **not determinable**). Document collabs have confirmed test-covered undo/redo (`collab-document/tests/document/redo_undo_test.rs`); no equivalent test or integration evidence was found for Database/DatabaseRow collabs — their undo/redo support is **not determinable / likely absent**, not confirmed either way.
10. **How are offline edits to databases handled — dedicated queue or shared mechanism?** Confirmed (upstream source) — shared, generic: one `AppFlowyCollabBuilder` factory constructs every collab object (Document, Folder, Database, DatabaseRow, WorkspaceDatabase, UserAwareness) through the identical local-first RocksDB-plugin + cloud-sync-plugin pipeline; there is no database-specific offline outbox.
11. **How do database changes propagate to other connected clients?** Confirmed (upstream source) — identical broadcast mechanism as documents: one generic per-object `CollabGroup` with a broadcast channel per `object_id`, taking `collab_type` only as metadata (persistence partitioning, Document-only indexing gate), not as a different propagation path.

### 4.1 Recommendations (explicitly NOT upstream fact — this document's own design judgment, not yet implemented or decided)

- **Can the existing doc-collab infra be reused as-is for database metadata/views?** Plausible for transport/persist-before-ack/Rid allocation at the *object* level (upstream itself treats Database as "just another CollabType" on the same generic pipeline — strong structural precedent). **Not** reusable as-is once rows become independent objects too (confirmed upstream model, §4 Q3): the backend's current `mutate()`/transaction boundary is scoped to one object at a time; N rows means N additional independently-synced objects, each needing Rid-stream and WS-subscription handling — an extension, not a drop-in, and should be explicitly scoped in Phase 3 rather than assumed free.
- **Should cells be relational values with a collaborative wrapper, or inside a Yjs document?** Recommendation: keep cells embedded in whatever row representation is chosen, not split into a separate relational per-cell table — upstream itself doesn't split them out either (§4 Q4), and a relational per-cell schema would be over-engineering relative to upstream's own flat-map design.
- **What should happen on concurrent same-cell edits?** Recommendation: a simple last-write-wins at the field/cell level (ordered by the existing Rid/mutate() single-writer boundary) is upstream-equivalent and sufficient; no new merge algorithm is required to match upstream fidelity. A genuine Yjs character-level merge for rich-text cells specifically would be a deliberate *improvement beyond* upstream, optional, not a requirement — flag as out-of-scope-by-default.
- **What should happen when one client deletes a row another client is editing?** Recommendation: upstream's own behavior (orphan-and-leave, no fencing) is a real gap even upstream. Recommend the independent backend do better here by extending the existing `restore_id`/`generation` fencing pattern: bump a per-row (or per-database) generation on delete and reject in-flight cell-edit frames for that row with a new `ROW_DELETED`/`ROW_GENERATION_MISMATCH` error, mirroring `RESTORE_GENERATION_MISMATCH`. This is a backend-original improvement, not an upstream-matching requirement — label it as such in any future implementation task.
- **How should row ordering work under concurrent updates?** Recommendation: given the backend's existing single-writer `mutate()`/transaction serialization already removes the concurrent-reorder race that upstream's Yjs `Array` exists to solve, a simpler fractional-index or integer `sort_key` (recomputed under the same boundary already used for Rid allocation) is sufficient and avoids implementing a full Yjs Array CRDT merge. This is a deliberate simplification relative to upstream, justified by the backend's different (single-process, single-writer) deployment assumption — document this tradeoff explicitly, do not present it as "how upstream does it."
- **How should database restoration interact with row/cell state?** Recommendation: this is a net-new design decision, not an upstream-derived answer (upstream has no confirmed database-level restore feature at all, §3.3/§8). Three shapes are possible: (a) restore only the database/views object, leave rows untouched; (b) cascade restore to each row to a matching historical generation; (c) atomic combined snapshot of database+views+rows. Recommend (a) for Phase 1-3 scope (simplest, matches the existing document-restore precedent's object-at-a-time model) with (b)/(c) deferred to Phase 5 as an explicit open decision, not a default.
- **Can the existing Rid/generation-fencing mechanism be reused for rows/cells, or does it need extension?** Needs extension. Recommend one generation counter per database that also fences child row writes (coarser, reuses the existing single-counter-per-mutate() pattern almost unchanged) over one generation counter per row (finer-grained but multiplies bookkeeping and requires a cascade-on-restore decision) — unless per-row restore granularity becomes an explicit product requirement.

## 5. Part D — Backend architecture proposal

### 5.1 Three storage-model options, evaluated

**Option A — fully relational.** Database/view/row/property/cell metadata all in relational tables (e.g. `databases`, `database_views`, `database_fields`, `database_rows`, `database_cells` with a typed-column-per-type or EAV shape).
- Frontend compatibility: **Poor.** 30 of the 35 operations in §2.2 are implemented against a Yjs read/write model (`YDatabase`/`YDatabaseView`/`YDatabaseRow` maps dispatched through `dispatch.ts`), not a REST CRUD surface. A pure-relational backend would require either (a) a REST shim the frontend doesn't currently call for most of these operations (large frontend-change surface, violating this project's "frontend is the default compatibility target" constraint), or (b) serializing relational state into a synthetic Yjs envelope on every read/write anyway — which is most of Option B's cost without Option B's benefit.
- Upstream compatibility: **Poor.** Upstream's own design is not relational at the collab layer at all (§3-4).
- Query performance: **Best** of the three for filter/sort/group at scale (native SQL).
- Collaboration complexity: **Lowest** (no CRDT machinery) but this is a false economy given (a) above.
- Postgres complexity: Moderate (new tables, no new patterns).
- JSON-mode cost: Would need an equivalent in-memory relational shape — awkward fit for the existing JSON-file single-blob-per-object convention.
- Migration complexity: Low initially, high later if frontend compatibility gaps force a rework.
- Version-history interaction: Would need a new, format-specific history mechanism (rows are many small rows, not one blob — the existing tombstone-snapshot pattern doesn't map cleanly).
- Backup/recovery: Simple (ordinary table backup).
- Future scaling: Good for read-heavy relational queries; poor for a real-time collab client that already expects CRDT-shaped sync.
- Data-inconsistency risk: Moderate — a shadow translation layer between relational truth and the Yjs shape the frontend expects is itself a consistency risk.
- **Verdict: not recommended** — would require unplanned frontend changes or a costly shim, against the instruction to avoid frontend changes unless unavoidable.

**Option B — hybrid relational + collaborative (RECOMMENDED).** Relational tables for metadata/catalog listing/authorization/indexing (database registry row, view registry row, field registry row for query-engine use), with the actual collaborative state (database+fields+views as one Yjs-syncable object; each row as one Yjs-syncable object, matching upstream's object graph) stored and synced through the **existing collab-admission/persistence pattern** (the same `store.*` generic-method interface, same JSON-blob-per-object convention in JSON mode, same `collab_updates`/binary-state-plus-state-vector convention in Postgres mode) that already serves Document and (trivially) WorkspaceDatabase objects.
- Frontend compatibility: **Good.** The frontend's Yjs dispatch layer reads/writes exactly this shape already; no frontend changes required for the Yjs-synced 30 operations. The REST-shaped operations (create/duplicate/move database, create row, CSV import, row-document materialization) get real routes matching the frontend's already-declared contracts (§2.3) — again no frontend changes required.
- Upstream compatibility: **Good.** Mirrors upstream's actual object graph (WorkspaceDatabase catalog → Database object → N DatabaseRow objects → optional Document-for-row-detail) and its `CollabType` numbering, without requiring upstream's literal Rust/Yrs crate.
- Query performance: relational *metadata* (field list, view list, row-order index) can be queried/filtered via SQL in Postgres mode for catalog/listing purposes; filter/sort/group over actual cell *values* still requires decoding each row's Yjs state (see §7 — this is the one place Option B pays a real cost relative to Option A, mitigated by maintaining a denormalized relational cell-value index, described in §7.3).
- Collaboration complexity: **Moderate** — reuses existing machinery for the object-level sync (no new protocol), but multiplies the number of synced objects by row count (§4.1's flagged risk) and needs new generation-fencing semantics for row deletion (§4.1).
- Postgres complexity: Moderate-high — new tables for registry/index data, plus new collab-object storage rows for Database/DatabaseRow objects (structurally identical pattern to the existing `collab_documents`/`collab_updates`/`collab_versions` tables, just keyed by object type).
- JSON-mode cost: Moderate — one more object kind (or two: Database, DatabaseRow) alongside Document in the JSON blob convention; registry/index data can live as plain JS objects/arrays in the same file, consistent with existing JSON-mode patterns.
- Migration complexity: Additive only (new tables/collab-object kinds), consistent with every migration so far in this project (001-006) — no changes to existing Document tables required.
- Version-history interaction: The existing tombstone-snapshot-restore pattern can be extended per-object (database object, each row object) without redesign, since each is already a separately-identified collab object (§4.1's recommendation (a)).
- Backup/recovery: Same backup posture as today's Document collab objects plus ordinary relational table backup for the registry/index tables.
- Future scaling: Registry/index tables scale normally; collab objects scale per-row the same way upstream's own design does (a tradeoff upstream itself accepted) — mitigate with the denormalized index (§7.3) rather than scanning Yjs state for every query.
- Data-inconsistency risk: Moderate — the registry/index tables must be kept in sync with the authoritative collab object state (the collab object remains the source of truth; the index is derived and must be rebuildable). This is a real, manageable risk, not a blocker — the same shape of risk the project already accepted for `workspaceRids`/dedup-digest bookkeeping alongside Document state.
- **Verdict: recommended.**

**Option C — upstream-compatible collaborative model, byte-for-byte.** Reproduce upstream's exact Yjs map/array layout and CRDT semantics (true multi-writer merge, real Yjs library use for Database/DatabaseRow objects, not a simplified JSON-blob-plus-digest convention), aiming for wire-level interop with a real AppFlowy desktop/mobile/cloud client.
- Frontend compatibility: **Best in theory**, but the independent backend doesn't currently implement true multi-writer Yjs merge for Document either (Task 46 confirmed ordering is via single-writer `mutate()` serialization, not CRDT merge across concurrent writers) — so Option C would require a new capability (real CRDT merge) that nothing else in this codebase has, for a self-hosted deployment where the existing single-writer boundary already provides adequate correctness for the realistic small-team concurrency level.
- Upstream compatibility: **Best**, but **not needed** for this project's actual goal (serving AppFlowy-Web, not interoperating with the Flutter/desktop client or AppFlowy Cloud's wire format byte-for-byte — no requirement for that was found in any task's scope).
- Query performance: Worst of the three without also building Option B's relational index on top anyway.
- Collaboration complexity: **Highest** — a real CRDT merge implementation is a substantial, high-risk undertaking disproportionate to this project's actual single-writer architecture.
- Postgres/JSON cost, migration complexity, version-history interaction, backup/recovery, scaling, inconsistency risk: all comparable to or worse than Option B, for no realized benefit given the frontend only needs the *shape* of the sync, not literal wire interop with other AppFlowy clients.
- **Verdict: not recommended** — picking this "because it's most upstream-faithful" would be over-engineering relative to actual requirements; Option B already captures upstream's object-graph shape and `CollabType` numbering (the parts that matter for frontend compatibility) without committing to upstream's full CRDT merge semantics (which nothing in this project currently needs or has).

### 5.2 Recommended repository interfaces (JSON and Postgres both satisfy the same shape — not implemented, design only)

Following the existing `store.*` generic-method convention (same names called from `server.js` regardless of storage mode):

```
// Database repository
store.createDatabase(workspaceId, { databaseId, primaryViewId, creatorUserId }) -> DatabaseRecord
store.getDatabase(databaseId) -> DatabaseRecord | null

store.setActiveDatabaseView(databaseId, viewId)  // if persisted server-side at all; may be client-only per current frontend behavior (§2.2 op 11)

// Row repository (each row is its own collab object per §3.3/§4 Q3)
store.createDatabaseRow(databaseId, { rowId, cells, position })
store.getDatabaseRow(rowId) -> RowRecord | null
store.updateDatabaseRow(rowId, { cellsPatch })

// Property/field repository
store.createDatabaseField(databaseId, { fieldId, name, fieldType, typeOptions })
store.updateDatabaseField(fieldId, patch)
store.deleteDatabaseField(fieldId)
store.reorderDatabaseFields(databaseId, orderedFieldIds)

// Cell repository (may be folded into the row repository rather than separate, per §4.1's
```

## 7. Part F — Query engine design (not implemented — design only)

### 7.1 Representation
Filters/sorts/groups are **per-view** state (confirmed upstream, §3.2) stored inside the Database collab object's view substructure. The query engine itself should be a **backend-authoritative service**, not duplicated client/server logic (per this project's non-negotiable constraint) — the frontend's own filter/sort/group evaluation (confirmed extensive, §2.2 ops 24-26) should be understood as the *client-side preview/optimistic* layer only; final persisted-query results for pagination/large-dataset cases must come from the backend's query engine, consistent with how this project already treats the frontend's offline/optimistic Yjs state as provisional until server-confirmed (the existing sync-outbox convention).

### 7.2 Filter operators per property type (design proposal)
- Text (RichText/URL/Email-if-added): equals, contains, starts-with, ends-with, is-empty, is-not-empty.
- Number: equals, greater-than, less-than, between, is-empty.
- Checkbox: is-checked, is-unchecked.
- Single/Multi-select: is, is-not, contains-any-of, contains-all-of, is-empty.
- Date: on, before, after, within-range, is-empty — timezone handling must be made explicit (upstream's own convention was **not determinable**, §3.10, so this is a net-new decision: recommend storing/filtering in UTC with client-local display conversion only, to avoid the undetermined-upstream-timezone risk entirely).
- Relation: contains-row, is-empty (deferred to Phase 4 per §3.6's precedent that even upstream's own REST API excludes Relation).
- Checklist/Media/Person/CreatedBy/LastEditedBy/Formula/Rollup: deferred pending §11's open decision on which of these are even server-backed.

### 7.3 AND/OR nesting, stable ordering, grouping, pagination
AND/OR nesting: the frontend's filter tree (confirmed, `dispatch/sort-filter.ts`, ~1,177 lines) already models nested AND/OR — the backend query engine's filter evaluator should accept the same tree shape (translated, not reinvented) so there is one filter-semantics definition, not two. Multiple sorts: evaluate in declared order, each a stable tiebreak for the previous (standard multi-key sort). Stable ordering: row order itself (§4 Q7/§4.1's recommended sort_key) is the final tiebreak when all explicit sorts are equal, guaranteeing deterministic pagination even with ties. Grouping: compute as a post-sort partition over the already-filtered/sorted result, consistent with how Select/Date/Number grouping already behaves in the frontend (confirmed code exists for all three). Empty/null values: group into a dedicated "no value" bucket (do not drop silently) for every property type. Invalid filter values (e.g. a filter referencing a deleted field or select option): the backend should return a validation error for the specific filter clause rather than silently dropping it or 500ing — mirrors this project's existing validation-error conventions elsewhere in `server.js`. Pagination: cursor-based (not offset), keyed on the stable sort_key tiebreak, consistent with how the frontend builds incrementally-synced Yjs row sets rather than classic page-N UI. Large datasets: push filter/sort evaluation into Postgres SQL where the denormalized cell-value index (below) makes that possible; fall back to in-process evaluation over decoded row state in JSON mode (consistent with JSON mode's existing "smaller deployments, no need for DB-level query pushdown" posture elsewhere in this project).

### 7.4 JSON/Postgres parity and pushdown
Recommend maintaining a **denormalized relational index table** (Postgres mode only; JSON mode evaluates in-process over its in-memory row objects, consistent with existing JSON-mode conventions) that mirrors each row's typed cell values in queryable columns (e.g. one JSONB column per row keyed by field id, or a narrower typed-columns-for-common-types approach) — kept in sync whenever a row's collab state is admitted (same point where Rid allocation already happens, so index maintenance can piggyback on the existing single-writer/transaction boundary with no new consistency hazard). This lets Postgres mode push filter/sort/group into native SQL (`WHERE`/`ORDER BY`/`GROUP BY` against the index table) for performance at scale, while JSON mode does the equivalent filtering/sorting in application code over the same logical row objects — preserving behavioral parity (same filter semantics, same result ordering) without requiring JSON mode to have a query planner. This index is explicitly **derived, rebuildable state** (the collab object remains authoritative) — a index-rebuild-from-source operation should exist from day one, not be an afterthought, to bound the data-inconsistency risk flagged in §5.1.

## 8. Part G — Security and permissions (design only)

### 8.1 Current state (confirmed by direct code inspection)
`requireWorkspace()` (`server.js:107`) is the only authorization primitive used by nearly every route — it checks session validity and workspace-membership existence, nothing finer. A `role` field (`owner`/`admin`/`member`) exists on membership records but is confirmed used in only one place found (`server.js:1125`, a test-only development-membership helper gated behind an explicit dev-key + non-prod-environment check) — there is **no confirmed role-differentiated write-permission enforcement** on any real production route. WebSocket authorization (`server.js`'s upgrade handler) performs the same workspace-membership check, nothing finer. There is no per-document, per-database, or per-row grant model of any kind.

### 8.2 Required authorization checks for database functionality (design proposal, not implemented)
- **Database creation**: workspace membership (existing check) — any member can create, matching current page-creation permissiveness (no evidence upstream or in this project of a stricter creation gate).
- **Database read**: workspace membership, **plus** (once real sharing exists, Milestone 3) a per-document/per-database grant check extending the same mechanism documents will use — do not build a database-specific permission model in parallel with the Milestone-3 sharing model; they must be the same check applied to a different object type.
- **Database update/delete**: workspace membership today; recommend reusing whatever ownership/role differentiation Milestone 3 introduces for documents (do not invent a database-specific owner concept first).
- **View changes**: same as database update (views live inside the database's own collab object, §3.2 — there is no independent view-level permission surface upstream or in this project's existing model).
- **Row creation/modification**: workspace membership today; same caveat as database update — recommend not inventing row-level ACLs ahead of the general sharing model, since no evidence (upstream or frontend) suggests row-level permissions distinct from database-level ones are needed for Phase 1-4 scope.
- **Property/field changes**: same as database update — schema changes should arguably require a stricter check than plain membership (a single member renaming/deleting a field affects every other member's view) — flag this as an **open product decision** (§11), not a default; the safest *interim* default (consistent with today's permissive page-creation model) is membership-only, revisited once Milestone 3's role model lands.
- **Cell updates**: workspace membership today — this is the highest-frequency operation and should not get a heavier check than row modification.
- **Database export (CSV/PDF)**: workspace membership — no additional restriction found upstream or justified by this project's own patterns.
- **Database collaboration (WS)**: workspace membership, exactly mirroring how Document WS auth works today — extend the existing collabType gate (§2.3/§4) to admit 1/3/4 under the same membership check, not a new one.

### 8.3 Minimum permission model for a first database release
Workspace-membership-only (matching the existing Document model) is **sufficient and consistent** for Phase 1-3 (§9) — do not block database functionality on Milestone 3's sharing/role work landing first; they are parallelizable (per `MASTER_FEATURE_ROADMAP.md`'s existing Milestone 2/3 dependency note). The one authorization assumption that **must** be resolved before database functionality is exposed to multiple users with differentiated trust levels (i.e. before any real multi-tenant/external-sharing use of this feature): whether field/schema changes (which affect every other viewer of the database) need a stricter check than plain membership — this is explicitly listed as unresolved in §11, not quietly deferred.

## 9. Part H — Version history and database recovery (design only)

Databases do need their own recovery story — **document version history does not automatically cover database state**, because a database's state lives in separate collab objects (Database object + N row objects, §3-4), not inside any Document object's history. Recommendation, extending the existing Tasks 49A/49B/57 tombstone-snapshot-restore pattern per-object rather than inventing a new mechanism:

- **Database-object snapshots** (metadata/fields/views): yes, needed — reuse the existing `createCollabVersion`/`listCollabVersions`/`restoreCollabVersion` shape verbatim, scoped to the Database object's own `object_id`/`collab_type=1`, exactly how it already works for Document (`collab_type=0`). No new mechanism required, just a new `collab_type` value accepted by the existing routes.
- **Row-level version history**: recommend **not** building per-row snapshot history in Phase 1-5 scope by default (§4.1's recommendation (a)) — row deletion should be a tombstone (soft-delete, consistent with the existing trash pattern, §9 below) rather than a version-history-tracked object; full per-row undo/redo was not even confirmed to exist upstream (§3.3/§4 Q9), so this is not a parity requirement, and building it preemptively risks the same N-multiplication-of-bookkeeping concern flagged in §4.1/§5.1.
- **Deleted rows**: can be restored via **trash** (tombstone with `deleted_at`, mirroring the existing page-trash pattern, Task 53) rather than via version-history restore — this is a simpler, already-proven pattern in this codebase and matches upstream's own "unlink, don't hard-delete" row-removal behavior (§3.3/§4 Q9) closely enough to be a faithful choice, not just a convenient one.
- **Schema/property changes**: should be revertible via the Database object's own version history (field add/remove/type-change are all mutations to the Database collab object per §3.2/§3.4, so they're automatically covered once Database-object snapshots exist — no separate mechanism needed).
- **Effect of a database restore on active clients**: reuse the existing restore-generation-fencing mechanism (`restore_id`/`generation`, Task 45) applied to the Database object — an in-flight field/view edit carrying a stale `restore_id` is rejected with the same `RESTORE_GENERATION_MISMATCH` pattern already proven for documents. Row edits in flight at restore time are a **separate, new fencing concern** (§4.1's `ROW_DELETED`/`ROW_GENERATION_MISMATCH` recommendation) since rows are independent objects not covered by the Database object's own generation counter — this is the one place database restore genuinely needs new fencing semantics beyond a direct copy of the document pattern, and should be scoped explicitly in Phase 5, not assumed to "just work" by analogy.
- **Generation fencing applicability**: per §4.1, recommend one generation counter per database that also fences child row writes (the coarser of the two options), to avoid multiplying per-row state before there's a confirmed product need for per-row restore granularity.
- **Backup/recovery coordination with collaborative state**: no new requirement beyond what already exists for Document collab objects — Database/DatabaseRow objects should back up the same way (full state + state-vector pair, Postgres table or JSON blob), with the same "nothing to compact, unbounded `collab_updates`-equivalent history growth is an open retention-policy decision" caveat already flagged project-wide in `ARCHITECTURE_OVERVIEW.md` §3(5) — do not treat database objects as needing a different retention policy than documents; they should inherit whatever retention decision Milestone 1 eventually makes for both.

### Task 63 addendum — Phase 1b completion detail, and two findings that affect later phases

Task 63 completed Phase 1b (above) for both the Database and DatabaseRow objects together. Two findings from that task matter for whoever picks up Phase 2 or later:

- **A pre-existing defect, not a Phase 1b design question, blocked Database creation in Postgres mode entirely until fixed**: migration 003's `pages.parent_view_id` foreign key only ever allowed a space as a page's parent; a Database's primary-view page is parented by its own container page (a page). - **The Database-catalog stub (§2.3, `GET .../database`) is now confirmed to be more than a cosmetic gap**: it is the exact, traced root cause of why a Database cannot be reopened from any browser session that did not itself just create it (fresh login, or a different real user's first open). - **Real-time broadcast model, relevant to Phase 5's "multi-client live propagation testing" item**: Task 63 traced directly (not assumed) that this backend's WebSocket handler relays `awarenessUpdate` only — no Document, Database, or DatabaseRow content update is ever pushed to another already-connected peer; every peer discovers a change via its own next `SyncRequest`. Phase 5 should design multi-client testing (and any future live-propagation feature) around this actual model, not an assumed push-broadcast model that does not exist today for any collab type.

### Task 64 addendum — the catalog stub is fixed, the "multi-client live propagation testing" blocker in Phase 5 is now removed, and one more route needed the same fix

Task 64 fixed exactly what the Task 63 addendum above recommended, then found the fix needed a companion fix in a second route before the real acceptance scenario actually worked. Full detail: `docs/TASK64_DATABASE_CATALOG_AND_FRESH_SESSION_NAVIGATION_REPORT.md`.

Phase 5's own "multi-client live propagation testing" item should now be read as: discovery/open is solved (this task), but live propagation while both clients stay connected is not, and remains future work with no code written toward it yet.
- **What's now the actual next concrete step**: Phase 2 (additional views/Grid-settings), or, if a future task's brief specifically calls for it, beginning the real-time content-broadcast work item above — not Phase 1b/1c (both fully done) and not another pass at the catalog/cold-open path (both fully done and evidenced).

## 13. Task 65 addendum — Database/DatabaseRow real-time collaboration gap is generic, not Database-specific, and its fix is now architecturally decided (investigation only, no implementation yet)

See `docs/TASK65_REALTIME_COLLABORATION_ARCHITECTURE_DECISION.md` for the full decision; summary relevant to this plan below.

**No change to this plan's own architecture is required.** Task 65's root-cause finding (the existing in-process `websocketPeers` awareness-relay pattern was never extended to content updates) and its recommended fix (extend that same pattern to the `Update` message path) are entirely orthogonal to the Database/DatabaseRow object-shape decisions this plan already made (fields+views+row-order arrays on the Database object, one independent object per row, generic cell writes via the shared Yjs-diff WS path) — the fix operates purely in the WS fan-out layer, after admission has already succeeded, regardless of which collab type or storage mode was involved. Nothing in §7 (repository interface design), §9 (version-history extension), or §11 (open decisions) needs revisiting as a result of this finding.

**One useful piece of corroboration for this plan's own risk register (§11 above)**: the "Row-as-independent-object multiplies Rid/WS-subscription bookkeeping by row count" risk row already anticipated that per-object subscriber bookkeeping would eventually matter; Task 65's trace of upstream's actual mechanism confirms upstream faces and accepts exactly this cost too (its `CollabGroup`/`Workspace` actor rosters scale with concurrently-open objects/sessions, not with total row count, the same shape of cost this backend's proposed fix would have) — i.e. this is a known, accepted, upstream-precedented cost of the chosen design, not a novel risk this backend's Option B fix would introduce.

**If Task 65's recommended fix is approved and implemented in a future task**, this plan's Phase 2+ work (additional views/Grid-settings, relations/rollups) can proceed exactly as already planned — the fix does not gate or change the sequencing recommended in §10/§12 above; it is a cross-cutting improvement to an already-shared layer, not a Database-feature-roadmap item in its own right.

## 14. Task 72 addendum — Phase 2 (additional database views) implemented; this plan's §3.2/§4 predictions confirmed exactly, §11 open-decision #2 narrowed

Full detail: `docs/TASK72_DATABASE_VIEWS_DISCOVERY.md`, `docs/TASK72_DATABASE_VIEWS_IMPLEMENTATION_REPORT.md`.
