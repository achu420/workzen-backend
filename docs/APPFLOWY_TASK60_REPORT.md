## Important findings (see `DATABASE_ARCHITECTURE_AND_IMPLEMENTATION_PLAN.md` for full detail)

1. **The frontend database implementation is deeper and more faithfully upstream-aligned than Task 58's single-stub framing suggested, but the backend gap is also larger than Task 58 found.** At least 15 distinct frontend-declared endpoints beyond the one known stub have zero backend implementation (atomic database/view/row creation, CSV import, row-document duplication, database history/blob-diff, orphaned-view materialization, and others — full list in the architecture doc §2.3/§6). More structurally: the backend's WebSocket handler has **no branch at all** for `CollabType` 1 (Database), 3 (Folder), or 4 (DatabaseRow) — only 0 (Document) and 2 (WorkspaceDatabase placeholder) are handled. This is a protocol gap, not just missing REST routes: even adding every missing REST route would not fix real-time database sync without this WS-layer change.
2. **Upstream's actual database architecture (confirmed by reading real pinned-revision source) is a graph of linked Yjs collab objects, not one document and not a relational schema**: a per-workspace `WorkspaceDatabase` catalog object; one `Database` object per database (fields + views + per-view row-order arrays only — no row content); one independent `DatabaseRow` object per row (`CollabType::DatabaseRow=4`); and, lazily, one `Document`-type object per row-detail page (same collab type as an ordinary page, id derived deterministically via UUIDv5 from the row id). `Database::encode_database_collabs()` explicitly confirms this by producing N+1 distinct encoded collabs (1 database + N rows) on export.
3. **Cells are not individually-addressable CRDTs upstream** — they are flat `HashMap<String, Any>` maps written via whole-map overwrite (Yjs `Map.fill`), i.e. last-write-wins at cell granularity even for RichText-typed cells (no YText). Row ordering, by contrast, **is** genuine CRDT state — a per-view Yjs `Array` of `{row_id, height}` references.
4. **No native upstream Rollup field type exists, and no CreatedBy/LastEditedBy field type exists either** — both independently re-confirmed by two separate research passes reading different parts of the source (absence from the `FieldType` enum values 0-14, and absence of any dedicated type-option/service file for either). The frontend's own `FieldType` TypeScript enum, however, includes `Rollup=16`, `CreatedBy=17`, `LastEditedBy=18`, `Person=15`, and `Formula=19` with substantial dedicated test coverage — a genuine, previously-undocumented frontend/upstream contract divergence that must be resolved as an explicit product decision (listed in the architecture doc §11) before any server-side implementation of these five types.
5. **Relation fields have real upstream complexity and are explicitly excluded even from AppFlowy-Cloud's own REST API** (`UNSUPPORTED_FIELD_TYPES = &[FieldType::Relation]`) — useful precedent for deferring Relation to its own dedicated design pass rather than folding it into general field-type work.
6. **Database-level version history/restore has no confirmed upstream precedent at all** — the frontend's `database-history-api.ts`/blob-diff contract appears to be a frontend-declared contract with no located upstream server implementation. This backend's existing document version-history mechanism (Tasks 49A/49B/57) does not automatically cover database state, because database/row state lives in separate collab objects entirely outside any Document object's history — a new, but structurally reusable, extension is needed (architecture doc §9).
7. **Authorization for database functionality does not exist beyond plain workspace membership** — re-confirmed by direct code inspection of `requireWorkspace()` (`server.js:107`), the sole authorization primitive used by nearly every route. A `role` field exists on membership records but is confirmed used in only one place (a test-only development-membership helper), not in any real production authorization check.

## Confirmed vs. inferred, rigorously distinguished

- **Confirmed by direct code inspection** (this task, not inherited from a prior report): the database-list stub text and line number, the WS collabType gate's absence of branches for 1/3/4, the full-sync-batch per-item type gate, the collab-GET route's `'0'`/`'2'` whitelist, `requireWorkspace()`'s membership-only scope, the migration-file registration pattern, the backend's continued absence of `.git`.
- **Confirmed by upstream source inspection** (by the two parallel research passes, cross-corroborated): the `CollabType` enum and its exact numeric values; the Database/DatabaseRow/WorkspaceDatabase object graph and which object holds what; cell-level last-write-wins semantics; row-order-as-CRDT-array semantics; row-detail-page-as-Document-object mechanism and its UUIDv5 derivation; absence of Rollup/CreatedBy/LastEditedBy upstream; Relation's explicit exclusion from AppFlowy-Cloud's REST API; the generic (not type-specific) WS/broadcast/persistence pipeline shared across all collab types.
- **Confirmed by static frontend code inspection**: the 35-operation classification table, the exact API contracts (paths/payloads) in the architecture doc §2.3, the row-detail-page mechanism, the `FieldType`/`Types`/`DatabaseViewLayout` enum values.
- **Not determinable from available source, explicitly flagged rather than guessed**: whether row-unlink ever triggers hard-deletion of the orphaned row's collab object upstream; whether Database/DatabaseRow collabs have any undo/redo support upstream (Document does, confirmed by test files; no equivalent test or integration evidence was found for Database/DatabaseRow); DateTime timezone-handling convention upstream; exact `Cell`/`DatabaseView` struct field lists beyond what's used at call sites; exact `FilterMap`/`SortMap` collab type names (only `GroupSettingMap`/`LayoutSettings`/`FieldSettingsByFieldIdMap` confirmed by name via import statements).
- **Recommendations, explicitly labeled as this document's own design judgment and NOT upstream fact or an implemented decision**: the Option B (hybrid relational+collaborative) storage-architecture recommendation; the repository interface sketches; the per-database (not per-row) generation-fencing granularity recommendation; the sort_key-instead-of-Yjs-Array row-ordering simplification (justified by this backend's different single-writer deployment assumption, not an upstream-matching claim); the `ROW_DELETED`/`ROW_GENERATION_MISMATCH` fencing extension for concurrent row-delete-vs-cell-edit (an improvement beyond upstream's own looser behavior, not a parity requirement); the denormalized query-index design for Postgres-mode filter/sort pushdown; the entire five-phase implementation plan and risk register.

- The commercial reference repo was confirmed to contain no source code at all; this means the "commercial reference ONLY, never copy from it" constraint could be honored trivially (there was nothing there to copy), not because of unusual discipline — this is recorded accurately rather than overstated.
