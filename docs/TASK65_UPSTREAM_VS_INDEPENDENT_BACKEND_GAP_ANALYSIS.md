# Task 65, Stage 2/3 — Upstream vs. Independent-Backend Gap Analysis and Root-Cause Diagnosis

Depends on: `docs/TASK65_UPSTREAM_COLLABORATION_ARCHITECTURE_AUDIT.md` (Stage 1, upstream side) and direct re-reading of this backend's own `server.js`/`storage.js` this task (independent-backend side). Classification legend, applied to every row: **Missing capability** / **Different implementation** (same outcome, different design) / **Intentional simplification** / **Protocol mismatch** / **Frontend limitation** / **Infrastructure limitation** / **Unverified**.

---

## 1. This backend's current mechanism (verified this task by direct code reading, not inherited from Task 63's prose)

**Verified source behavior**, `AppFlowy-Independent-Backend/server.js`:
- A single process-wide `websocketPeers = new Set()` (`server.js:1575`) holds every currently-open WebSocket, across every workspace and every object, added on successful auth/handshake for each collab-type branch (Document `server.js:1750`, Database `server.js:1907`, DatabaseRow `server.js:2068`, and a fourth generic path `server.js:2189`), removed on close/error (`server.js:2234,2237`).
- **Content updates** (`collabMessage.update`, any of the three collab types): the handler calls the storage layer's `accept*CollabUpdate` (persist-before-ack; already proven by fault injection in Tasks 44/61/62 — not re-derived here), then sends exactly two frames **back to the same `websocket` that sent the update**: an `Update` echo carrying the server-assigned `messageId` (Document: `server.js:1788-1798`; Database: `server.js:1945-1955`; DatabaseRow: `server.js:2106-2116`) and a manifest/state-vector frame. **No iteration over `websocketPeers` occurs anywhere in any of these three accept paths.** Re-verified live this task: `npm run test:postgres`'s `postgres-database-multiclient.test.js` fixture ("PostgreSQL multi-client (WebSocket protocol level): neither atomic REST row creation nor an ordinary WS cell update broadcasts to another connected peer") was run fresh (not just read) and passed, logging `REST row creation broadcast check: peer received NOTHING` and `Ordinary WS cell-update broadcast check: peer received NOTHING` — i.e. the absence of broadcast is a live, reproduced runtime observation this task, not merely a static-code claim.
- **Awareness updates** (`collabMessage.awarenessUpdate`): the handler *does* iterate `websocketPeers`, filtering to the same `workspaceId` and same `objectId` as the sender and excluding the sender itself, and relays the raw encoded frame to every match (Document: `server.js:1822-1830`; Database: `server.js:1979-1987`; DatabaseRow: `server.js:2140-2148`; generic: `server.js:2215-2223`).
- This backend's protocol (`collab-protocol.js:38`) is wire-compatible with upstream's real `collab.CollabMessage` oneof (`syncRequest|update|awarenessUpdate|accessChanged`) — confirmed in the companion audit document §0 and by Task 60.5. The `Update` message's `messageId` field is reused by this backend as a self-ack; nothing in the protocol or the frontend forbids this (companion audit §3).

## 3. Root-cause diagnosis: why doesn't an already-connected second client see Client A's change?

**The question posed by the task brief is answered with evidence, not assumed**: is the cause (a) a missing upstream message flow, (b) a missing client-side sync trigger, (c) a mishandled protocol message, (d) unshared collaboration state between sessions, (e) a WS handler that fails to register a subscriber, (f) a never-emitted event/callback, or (g) an additional sync-engine step upstream performs that this backend doesn't?

**Answer, verified by direct code reading of both sides**: it is **(e) combined with (f)**, narrowly — and explicitly **not** (b) or (c).

1. **Not (b) — no missing client-side trigger.** §3 of the companion audit document proves, by reading `AppFlowy-Web/src/application/services/js-services/sync-protocol.ts:220-254,384-400`, that the frontend's `handleUpdate`/`handleMessage` dispatch already applies *any* incoming `Update` frame for a currently-open object unconditionally, with no distinction between "this is my own ack" and "this is a push from another client." The frontend requires zero changes to start reflecting a server-pushed update live.
2. **Not (c) — no mishandled protocol message.** The `Update` message shape this backend would need to send to a peer is byte-for-byte the same shape (`collab.Update`/`messages.collab.CollabMessage`) it already successfully sends to the *originating* socket as an ack, and the same shape upstream's `Workspace` actor sends in its own broadcast step (`ServerMessage::Update`, `workspace.rs:438-446`). There is no protocol gap to design around.
3. **It is (e)/(f): this backend's WS handler never registers, and never consults, a subscriber/peer list for the `Update` message path, for any of the three collab types** — even though the exact same process-wide `websocketPeers` registry (declared `server.js:1575`, populated at `server.js:1750/1907/2068/2189`) already exists and is already filtered-and-iterated correctly for the sibling `awarenessUpdate` path (`server.js:1822-1830/1979-1987/2140-2148/2215-2223`). The three `Update`-admission code blocks (`server.js:~1780-1819` Document, `~1895-1973` Database, `~2056-2134` DatabaseRow) persist, ack the sender, and `return` — with no call into `websocketPeers` at all. This is a straightforward, scoped omission in an otherwise-complete pattern already proven to work for a sibling message type in the same file, not a deeper architectural absence.
4. **This is unambiguously a backend-side missing capability, not an upstream-infrastructure requirement.** Upstream's equivalent mechanism (§1.3 of the companion audit) needs Redis *because* upstream is designed for horizontal multi-instance scale-out, where a write landing on instance X must reach a reader's session on instance Y. This backend is explicitly, deliberately single-process (Task 60.5 §10/§11, Strategy A, unchallenged by this task). Within a single process, the in-memory `websocketPeers` set is a complete, correct substitute for "the set of all other joined sessions" — exactly analogous to how upstream's `Workspace.sessions_by_client_id` serves the same role in-memory *within one process* before Redis is even consulted for cross-process delivery. **No new infrastructure (Redis, a message broker, a second service) is required to close this specific gap** — only applying the same "iterate matching peers, skip sender, send the frame" step already written for awareness to the `Update` path as well.
5. Not (a), (d), or (g) in any form that implies a different *kind* of mechanism is needed: there is no missing upstream message *flow* (the flow is "admit → make visible to a live roster → done", already fully present in this backend for awareness); there is no "unshared collaboration state between sessions" in the sense of two sessions holding divergent server-side state (`storage.js`/`postgres-*-repository.js` is the single shared source of truth both sessions' next `SyncRequest` would read correctly — Task 63 already proved this); and there is no additional upstream sync-engine step being skipped (§1 of the companion audit shows upstream's "step" is exactly the same subscriber-fan-out idea, not something qualitatively richer).

## 4. Summary of genuine gaps found (for Stage 4)

Only one genuine, user-visible missing capability was found, and it is narrow:

- **Missing capability**: no live push of accepted content `Update`s to other already-connected sessions viewing the same object, for Document, Database, and DatabaseRow alike. User-visible impact: a second user (or the same user in a second tab/device) who already has the object open will not see Client A's edit until their own next `SyncRequest` (reconnect, tab refocus if that triggers a resync, or any other event that causes a fresh manifest exchange) — confirmed by this task's fresh live rerun of the `postgres-database-multiclient.test.js` fixture. Affects all three collab types identically (it is a generic gap in the shared WS-handler pattern, not type-specific). Single-process-only concern: fixing it does not require solving multi-process coordination, since this backend does not claim multi-process support today (that remains a separate, intentionally-deferred infrastructure limitation, not part of this gap). Responsiveness-only, not a data-integrity defect: durable state is always correct and consistent (proven by Tasks 42-64's persistence/ack/dedup test suites, all still green per this task's fresh baseline run); the gap only concerns *latency of visibility to other live peers*, not correctness of the eventually-synced result.

Everything else examined in §2's table is either already-equivalent-by-design, a deliberate and previously-documented simplification (workspace-membership-only authorization; single-process scope), or an area where this backend's own guarantees are stronger than upstream's (persist-before-ack, explicit admission validation, explicit duplicate dedup) rather than weaker.
