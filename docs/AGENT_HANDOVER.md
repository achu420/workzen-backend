## 5. Current architecture

### JSON mode

`storage.js` persists users, sessions, workspaces, memberships, page metadata, page Yjs state, atomic-creation request receipts, and WorkspaceDatabase Yjs state to a local file. The default Document creation transaction stores metadata and initial binary content together; the JSON file is atomically replaced on persist.

### PostgreSQL mode

`postgres-storage.js` runs the checked-in migrations and uses parameterized SQL for user/workspace/page behavior. Migration 003 adds page parent/presentation metadata and an atomic request ledger; page and collab-document inserts share one database transaction. WorkspaceDatabase state is stored in `workspace_database_collabs`, with a composite foreign key tying its object ID to the workspace's `database_storage_id`. `PostgresPageCollabRepository` stores canonical page Yjs binary state/state-vector rows and accepted binary payload metadata transactionally. PostgreSQL runtime behavior for Task 35 was not exercised because no isolated test database was configured.

### Collaboration boundary

`collab-protocol.js` contains a source-derived subset of AppFlowy `messages.proto`/`collab.proto`. The backend exposes authenticated WorkspaceDatabase (`collab_type=2`) and Document (`collab_type=0`) state reads, plus `GET /api/workspace/{workspaceId}/page-view/{viewId}`. A single Document WebSocket session can initialize and admit one-client Yjs updates to JSON storage before responding. An authenticated HTTP `/collab/full-sync/batch` path reconciles and persists Documents only; unsupported collaboration types return explicit per-item errors. Browser tests recovered an ordinary-text marker after reload and backend restart, but this proves neither multi-client convergence nor general sync compatibility. Redis stream semantics, robust reconnect/replay, multi-instance ordering, authoritative restore transitions, and WebSocket/HTTP convergence remain unimplemented or unverified.

## 6. Protocol blockers

The authoritative discussion is [APPFLOWY_SYNC_SEMANTICS_AND_ADMISSION.md](./APPFLOWY_SYNC_SEMANTICS_AND_ADMISSION.md). The exact evidence still needed is:

1. **`Rid` allocation and ordering:** determine whether IDs are workspace-stream, object, or resume cursors and how timestamps/counters are assigned. Need upstream server stream code and reconnect fixtures. Still pending.
2. ~~**Duplicate admission/retry**~~ — **Resolved by Task 41.** The server's own idempotency key (payload digest, optionally a caller `messageKey`) and replay response (same `messageId` returned, no re-application) are implemented and proven by a two-delivery integration fixture (`test/backend.test.js`). This is a documented, locally-chosen key, not a proven match to AppFlowy's own wire-compatible duplicate key — see `docs/APPFLOWY_TASK41_REPORT.md`.
3. **Realtime acknowledgement timing:** determine whether acknowledgement is a broadcast `Update`, a separate frame, or optimistic client behavior. Need a crash-window test around durable commit/send. Still pending (Task 41 classified the crash-injection infrastructure this needs as out of scope for a single safe slice).
4. **Compaction/history retention:** determine trimming, compaction, and missing-history recovery. Need upstream retention code and state-vector recovery fixtures. Still pending.
5. **Restore transitions:** determine authoritative generation changes, stale-write rejection, and notifications. Need database restore integration tests. Still pending.
6. **Cross-instance replay:** prove shared ordering, fan-out, failover, and restart recovery. Need two-instance upstream-stream tests. Still pending.
7. **WebSocket/HTTP convergence:** prove both lanes produce the same durable state and retirement semantics. Need an isolated end-to-end comparison fixture. Still pending — Task 41 found both lanes already share one storage-level admission function (`store.acceptPageCollabUpdate`), which is new supporting evidence, but no fixture yet proves convergence end-to-end. Recommended as the next smallest task.

Do not infer these from the local repository or call the prototype fully compatible.

## 9. Future MVP acceptance criteria

The first real MVP is **not complete**. It must eventually prove, using the actual AppFlowy-Web frontend:

1. An authenticated user opens an ordinary page through the independent backend's page-view contract.
2. The page loads a valid AppFlowy Yjs document and the user edits ordinary text.
3. The edit is durably admitted through the supported synchronization path and survives page reopen and application restart.
4. Unauthorized workspace/page access is rejected.
5. Retry/reconnect does not lose or duplicate the edit.
6. Two clients or independent backend instances converge on a basic concurrent edit without silent overwrite.

These are future acceptance goals, not completed functionality. Databases, invitations, files, search, presence, history, and advanced collaboration require additional acceptance suites.

## Task 59 — PostgreSQL migration advisory-lock fix (P0 concurrency defect)

Fixed the defect Task 56 found and Task 58 re-confirmed still present: `postgres-storage.js`'s `openPostgresStore()` reapplied its full migration DDL on every call with no coordination between independent processes, only worked around at the test level (`--test-concurrency=1`), which never protected production. **Reproduced with two real, independent OS processes** (no mocks) against a fresh disposable database on the unmodified pre-Task-59 code: one process completed in 140ms, the other hung indefinitely (Postgres server-side confirmed the connection had actually finished executing the whole migration and was idle, but the Node client never returned) and had to be force-killed after 3+ minutes.

**Fix**: a new `postgres-migration-lock.js` adds a Postgres **session-level** advisory lock (`pg_advisory_lock`/`pg_advisory_unlock`, bounded `pg_try_advisory_lock` retry loop with a documented, configurable timeout — not the blocking variant, which can't report progress or give up) keyed deterministically off `SELECT current_database()` hashed with SHA-256 into a signed bigint (same DB → same key across restarts; different DBs → different keys). Session-level (not transaction-level) was chosen because the critical section spans multiple independently committed per-file migration transactions, which a transaction-level lock cannot cover. `postgres-storage.js`'s `openPostgresStore` now: acquires this lock on its dedicated migration client before touching any schema → rechecks a new minimal `schema_migrations` tracking table under the lock (introduced because none existed and blind reapplication was exactly the premise that broke under concurrency) → runs only genuinely pending migration files, each in its own transaction (so a failed file is never recorded as applied while earlier, already-committed files stay correctly recorded) → releases the lock → releases the client → returns the repository, in that order on every path including failure. A second, related ordering defect found and fixed in the same work: the pre-Task-59 failure path called `pool.end()` from inside a `catch` while the dedicated client was still checked out and only released in a not-yet-run `finally` — `pg-pool`'s `end()` (confirmed by reading its source) does not resolve until every checked-out client is released, so this could itself deadlock on any migration failure; fixed by the same restructuring. No new external dependency (`node:crypto` only).

**Regression tests** (`test/postgres-migration-lock.test.js`, 10 tests, all against real Postgres via the real `pg` driver, no mocks even in the failure-path tests): lock-key determinism/distinctness/range; two real, distinct Postgres sessions contending for the same key with genuine wait-then-acquire timing; 2-way and 3-way concurrent `openPostgresStore()` against a fresh database with migrations applied exactly once; a forced-overlap test using a new, documented, env-gated, zero-cost-when-unset test-only delay hook (`POSTGRES_MIGRATION_TEST_DELAY_MS`); bounded lock-timeout error; release-without-holding error; real abrupt-socket-destruction connection-loss recovery; a **genuine** real Postgres `23505` unique-violation forced inside migration 001's own unique index (by dropping it and seeding real duplicate data) proving rollback, lock release, no misleading success row, and a successful corrected retry; and a no-op-recheck reopen test confirming zero leaked advisory locks. 10/10 passed.

**Real multi-OS-process verification (Part G, the primary acceptance evidence)**: two genuinely separate OS processes (not two promises in one process) called the actual production `openPostgresStore()` against the same fresh disposable database, with Process A's hold observably overlapping Process B's concurrent attempt (confirmed both by process timestamps and by an independent third-connection `pg_locks` monitor showing Process A's distinct Postgres backend pid holding the lock throughout); Process B then acquired the lock the instant A released it, rechecked, and completed with migrations applied exactly once (6, not 12). An extended scenario hard-killed (`kill -9`) a lock-holding OS process mid-hold, confirmed Postgres auto-released the session lock within ~1.5s, and confirmed a subsequent real process acquired it and completed cleanly — the database remained fully recoverable after a real crash while holding the lock.

**Test-level workaround removed**: `--test-concurrency=1` was dropped from `test:postgres` in `package.json` (now 4 files, 20 tests) since the production fix genuinely protects concurrent initialization now — verified by running the suite **5 times in a row at normal `node --test` concurrency** with 20/20 every time, no flakiness, no migration deadlocks.

## Task 65 — Real-time collaboration architecture investigation (INVESTIGATION ONLY, no implementation — awaiting approval)

**Purpose**: Tasks 63/64 observed, as a side finding, that no content update of any collab type broadcasts to other already-connected peers — only `awarenessUpdate` does. This task was explicitly scoped to investigate WHY, by tracing upstream's actual real-time collaboration architecture end to end (not assuming a WebSocket-broadcast fix is correct just because it seems obvious), compare it rigorously against this backend, diagnose the genuine root cause, evaluate architectural alternatives, and produce a decision document — with a mandatory stop before any implementation.

**Upstream has two parallel realtime stacks, and the one that matters is not the one found first.** `AppFlowy-Cloud/services/appflowy-collaborate` ships both a legacy per-object "collaboration group" design (`rt_server.rs`/`group/*`, routed at `/ws/v1`) and a current workspace-scoped actor design (`ws2/actors/{server,session,workspace}.rs` + `collab/collab_manager.rs`, routed at `/ws/v2/{workspaceId}` — the exact URL pattern AppFlowy-Web's real client, and this backend, actually use). Both were traced to function level; the live v2 design is what the Stage-2 comparison is grounded in. Confirmed (not assumed) that `appflowy-proto`'s Rust `ClientMessage`/`ServerMessage` types serialize via the same protobuf wire format as `AppFlowy-Web/src/proto/messages.proto` — no revision-skew/protocol-mismatch risk was found between the two checked-out repos.

**Upstream's actual broadcast mechanism, verified at the function level**: a single `Workspace` actor per workspace holds a live roster of every currently-joined session (`sessions_by_client_id`). A client's accepted `Update` is written to a Redis Stream keyed by workspace (`CollabManager::publish_update`, `collab/collab_manager.rs:239-278`) — with **no ack sent to the sender at all** in the live v2 protocol (confirmed: no CollabAck-equivalent message type exists in the current protobuf schema). The same `Workspace` actor, as that stream's own subscriber, reads the write back and iterates every OTHER joined session (skip origin, per-session-per-object permission re-check), pushing the identical `Update` frame to each (`ws2/actors/workspace.rs:394-461`). Awareness follows the exact same shape through a parallel Redis stream (`workspace.rs:464-489`). Durability to the long-term Postgres-backed store is fully decoupled and asynchronous (periodic snapshot, `workspace.rs:613-634`) — i.e. upstream's live protocol has a WEAKER synchronous durability guarantee at the moment of broadcast than this backend's persist-before-ack design has at the moment of ack.

**Root cause of the symptom, verified not assumed**: AppFlowy-Web's frontend (`sync-protocol.ts:220-254,384-400`) already applies ANY incoming `Update` frame for an open object unconditionally — it needs zero changes to support server-pushed live updates. The wire message shape needed is identical to the ack frame this backend already sends to the sender and identical to upstream's own broadcast frame — zero protocol changes needed. The actual, narrow cause: this backend's own `websocketPeers` registry (`server.js:1575`) is already correctly iterated, filtered by `workspaceId`+`objectId`, skip-origin, for the sibling `awarenessUpdate` message type at four call sites (`server.js:1822-1830/1979-1987/2140-2148/2215-2223`) — but the three `Update`-admission success paths (Document/Database/DatabaseRow) never consult it at all. This is a scoped, mechanical omission in an otherwise-proven-working pattern, not a missing architectural concept or missing infrastructure.

**Recommendation: Option B** — extend the exact pattern already proven correct for awareness to the `Update` message path, for all three collab types. No new infrastructure (no Redis, no second process, no new dependency), no protocol change, no frontend change. Explicitly rejected: adopting upstream's collaboration server/service (both stacks remain hard-coupled to Redis and to AppFlowy-Cloud's own auth/workspace schema — re-confirmed this task, including for the live v2 stack, not just the previously-examined legacy one); doing nothing (the frontend evidence shows the product's basic two-user scenario visibly fails to feel collaborative, independently reproduced this task via a fresh live rerun of `postgres-database-multiclient.test.js`); a BroadcastChannel-only fix (same-tab only, not cross-user); client-side polling (unrequested frontend change, strictly worse than the chosen fix); introducing Redis now (solves a multi-process problem this backend doesn't have).

**No code was changed.** Full regression baseline re-run fresh this task, all green and matching documented baselines exactly: `npm test` 38/38, `npm run test:offline-collab` 5/5, `npm run test:collab-conformance` 6 passed/0 failed/2 pending/5 resolved, `npm run test:database-collab` 13/13, `npm run test:database-row-collab` 11/11, `npm run test:database-catalog` 17/17, `npm run test:postgres` 43/43 (8 files, migration-lock 10/10 within it — required explicitly exporting `DATABASE_URL` in the same shell command as the test invocation, since this environment's shell state does not persist `export`s across separate tool calls; without it all 43 report SKIP, not fail), `npm run test:parity` 2/2.
